# 16

## Cel rozdziału

Rozdział 16 wprowadza współbieżność w Ruście. Główna teza: ownership i typy nie chronią tylko pamięci, ale też pomagają wyłapywać wiele błędów współbieżności już na etapie kompilacji.

Rozdział obejmuje trzy podstawowe modele pracy:

- wątki,
- message passing,
- współdzielony stan.

## Wątki: `thread::spawn`

Podstawowe uruchomienie nowego wątku:

```rust
use std::thread;

let handle = thread::spawn(|| {
    println!("hello from spawned thread");
});
```

`thread::spawn` przyjmuje domknięcie z kodem do wykonania w nowym wątku i zwraca `JoinHandle<T>`.

### Ważna właściwość

Jeśli główny wątek kończy się, wszystkie uruchomione wątki potomne są przerywane, nawet jeśli nie skończyły pracy.

## `join`

Aby poczekać na zakończenie wątku:

```rust
handle.join().unwrap();
```

`join`:

- blokuje bieżący wątek,
- czeka na zakończenie wątku reprezentowanego przez handle,
- zwraca `Result`, więc typowo widzi się `unwrap()`.

Miejsce wywołania `join` ma znaczenie: jeśli zrobisz to za wcześnie, stracisz realną współbieżność; jeśli za późno albo wcale, wątek może nie zdążyć skończyć.

## `move` w domknięciu wątku

Bardzo częsty idiom:

```rust
use std::thread;

let v = vec![1, 2, 3];

let handle = thread::spawn(move || {
    println!("Here's a vector: {v:?}");
});

handle.join().unwrap();
```

`move` wymusza przeniesienie ownership danych do domknięcia, a więc i do nowego wątku.

### Dlaczego to potrzebne

Bez `move` domknięcie mogłoby próbować tylko pożyczyć dane z wątku głównego. Kompilator nie może zagwarantować, że te pożyczki będą nadal ważne, gdy nowy wątek zacznie się wykonywać. `move` rozwiązuje ten problem przez transfer ownership.

## Message passing: kanały `mpsc`

Rustowy kanał z biblioteki standardowej ma model:

- **multiple producer**
- **single consumer**

Tworzenie kanału:

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();
```

- `tx` — transmitter / sender,
- `rx` — receiver.

## Wysyłanie wiadomości

```rust
use std::thread;
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    let val = String::from("hi");
    tx.send(val).unwrap();
});
```

`send` zwraca `Result`, bo może się nie udać, np. gdy receiver już nie istnieje.

### Ownership i `send`

`send` przejmuje ownership wysyłanej wartości. Po wysłaniu nie wolno jej już używać w wątku nadawcy. To jest bardzo ważna ochrona przed użyciem danych po ich logicznym przekazaniu innemu wątkowi.

## Odbieranie wiadomości

Blokujące odbieranie:

```rust
let received = rx.recv().unwrap();
println!("Got: {received}");
```

`recv`:

- blokuje, aż dostanie wiadomość,
- zwraca `Result<T, E>`.

Nieblokujące odbieranie:

```rust
let maybe_msg = rx.try_recv();
```

`try_recv` od razu zwraca wynik: albo wiadomość jest, albo nie.

## Receiver jako iterator

Kanał można też czytać idiomatycznie przez iterację:

```rust
for received in rx {
    println!("Got: {received}");
}
```

Iteracja kończy się, gdy wszystkie transmittery zostaną dropnięte i kanał się zamknie.

## Wiele producerów

To sedno `mpsc`: można sklonować transmitter.

```rust
let tx1 = tx.clone();
```

Potem różne wątki mogą wysyłać do jednego `rx`. Odbiorca widzi wspólny strumień wiadomości z różnych źródeł.

## Współdzielony stan: `Mutex<T>`

Drugi model współbieżności to wspólna pamięć, ale kontrolowana.

Podstawowe użycie `Mutex<T>`:

```rust
use std::sync::Mutex;

let m = Mutex::new(5);

{
    let mut num = m.lock().unwrap();
    *num = 6;
}

println!("m = {m:?}");
```

### Co daje `Mutex<T>`

- tylko jeden wątek naraz może wejść do chronionych danych,
- `lock()` zwraca guard,
- guard automatycznie zwalnia lock przy wyjściu ze scope.

To ważne: Rust wymusza model, w którym trudno „zapomnieć” o odblokowaniu mutexa, bo robi to `Drop` na guardzie.

## `Mutex<T>` między wieloma wątkami

Sam `Mutex<T>` nie wystarczy, jeśli kilka wątków ma współdzielić ownership tej samej blokady. Trzeba dołożyć wielowątkowy licznik referencji:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);
    let handle = thread::spawn(move || {
        let mut num = counter.lock().unwrap();
        *num += 1;
    });
    handles.push(handle);
}

for handle in handles {
    handle.join().unwrap();
}

println!("Result: {}", *counter.lock().unwrap());
```

To klasyczny wzorzec `Arc<Mutex<T>>`.

## Dlaczego nie `Rc<T>`

`Rc<T>` nie jest thread-safe. Próba użycia `Rc<Mutex<T>>` między wątkami kończy się błędem kompilacji, bo `Rc<T>` nie implementuje `Send`.

## `Arc<T>`

`Arc<T>` = atomically reference counted. Jest odpowiednikiem `Rc<T>` dla współbieżności.

- `Rc<T>` — single-threaded,
- `Arc<T>` — thread-safe, ale z kosztem atomików.

Interfejs jest praktycznie taki sam jak `Rc<T>`:

```rust
let data = Arc::new(value);
let other = Arc::clone(&data);
```

## Interior mutability a współbieżność

Rozdział wyraźnie porównuje:

- `Rc<T>` / `RefCell<T>` w single-threaded,
- `Arc<T>` / `Mutex<T>` w multi-threaded.

Analogiczna idea:

- `RefCell<T>` daje interior mutability z kontrolą w czasie działania,
- `Mutex<T>` daje interior mutability zsynchronizowaną między wątkami.

## Ryzyka logiczne

Rust mocno ogranicza data races i invalid references, ale nie eliminuje wszystkich błędów współbieżnych.

Rozdział wymienia m.in.:

- race conditions na poziomie logiki,
- deadlocki,
- trudne do reprodukcji błędy zależne od planowania wątków.

Szczególnie przy `Mutex<T>` dalej można stworzyć deadlock, jeśli źle zaprojektujesz kolejność zdobywania locków.

## `Send`

`Send` oznacza, że ownership wartości można bezpiecznie przenieść do innego wątku.

Praktycznie:

- prawie wszystkie podstawowe typy implementują `Send`,
- `Rc<T>` nie implementuje `Send`,
- `Arc<T>` implementuje `Send`, jeśli wewnętrzny typ też spełnia wymagania.

To właśnie dlatego kompilator blokuje użycie `Rc<T>` między wątkami.

## `Sync`

`Sync` oznacza, że typ może być bezpiecznie współdzielony przez referencję między wątkami.

Reguła praktyczna z rozdziału:

- typ `T` jest `Sync`, jeśli `&T` jest `Send`.

Ważne przykłady:

- `Rc<T>` nie jest `Sync`,
- `RefCell<T>` nie jest `Sync`,
- `Mutex<T>` jest `Sync` i właśnie po to istnieje.

## `Send` i `Sync` jako marker traits

To marker traits:

- nie mają metod,
- służą do wyrażania gwarancji bezpieczeństwa współbieżności.

Większość typów składających się wyłącznie z elementów `Send` / `Sync` automatycznie dziedziczy te właściwości.

Ręczne implementowanie tych traitów jest `unsafe`, bo łatwo byłoby złamać gwarancje języka.

## Kiedy który model

| Model | Narzędzie | Kiedy typowo |
|---|---|---|
| niezależne zadania | `thread::spawn` + `join` | gdy chcesz uruchomić kod równolegle |
| przekazywanie danych | `mpsc::channel` | gdy chcesz komunikacji bez współdzielenia pamięci |
| współdzielony stan | `Arc<Mutex<T>>` | gdy wiele wątków musi mutować wspólną strukturę |

## Co zapamiętać

1. `thread::spawn` uruchamia kod w nowym wątku, a `JoinHandle::join` pozwala poczekać na jego zakończenie.
2. `move` w domknięciu wątku jest standardowym sposobem transferu ownership do nowego wątku.
3. Kanały `mpsc` realizują message passing i domyślnie wymuszają bezpieczny transfer ownership wiadomości.
4. `send` przenosi wartość, a `recv` odbiera ją blokująco; receiver można też traktować jak iterator.
5. `Mutex<T>` chroni współdzielony stan i automatycznie zwalnia lock przez guard + `Drop`.
6. `Arc<T>` jest wielowątkowym odpowiednikiem `Rc<T>` i służy do współdzielonej własności między wątkami.
7. Typowy wzorzec dla wspólnego, mutowalnego stanu to `Arc<Mutex<T>>`.
8. `Send` i `Sync` opisują, czy typ jest bezpieczny do transferu albo współdzielenia między wątkami.
9. Rust eliminuje wiele klas błędów współbieżności na etapie kompilacji, ale nie zwalnia z projektowania poprawnej logiki synchronizacji.
