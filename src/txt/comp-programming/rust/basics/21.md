# 21

## Cel rozdziału

Rozdział 21 buduje końcowy projekt: prosty serwer HTTP oparty o TCP, a potem rozwija go do wersji wielowątkowej z własną pulą wątków i graceful shutdown.

To praktyczne złożenie kilku tematów z wcześniejszych rozdziałów:

- I/O,
- ownership,
- wątki,
- kanały,
- `FnOnce`,
- `Drop`.

## TCP i HTTP: minimalny model

Serwer działa nad TCP, a HTTP jest protokołem wyższego poziomu, który definiuje kształt requestów i odpowiedzi.

Dla projektu ważne są tylko podstawy:

- serwer nasłuchuje TCP,
- klient wysyła request HTTP,
- serwer czyta bajty, rozpoznaje prosty request i odsyła response.

## `TcpListener`

Start serwera:

```rust
use std::net::TcpListener;

let listener = TcpListener::bind("127.0.0.1:7878").unwrap();
```

To wiąże proces z lokalnym adresem i portem.

### `incoming()`

Obsługa połączeń:

```rust
for stream in listener.incoming() {
    let stream = stream.unwrap();
    println!("Connection established!");
}
```

`incoming()` daje iterator po próbach połączeń, a pojedyncze udane połączenie reprezentuje `TcpStream`.

## `handle_connection`

Pierwszy krok po uzyskaniu połączenia to odczyt requestu:

```rust
use std::io::{BufRead, BufReader};
use std::net::TcpStream;

fn handle_connection(stream: TcpStream) {
    let buf_reader = BufReader::new(&stream);
    let http_request: Vec<_> = buf_reader
        .lines()
        .map(|result| result.unwrap())
        .take_while(|line| !line.is_empty())
        .collect();

    println!("Request: {http_request:#?}");
}
```

To czyta liniami request aż do pustej linii, która w HTTP kończy nagłówki.

## Minimalne parsowanie HTTP

Książka nie buduje pełnego parsera HTTP. Wystarczy sprawdzić pierwszy wiersz requestu i zareagować na kilka prostych przypadków, np.:

- `GET / HTTP/1.1`
- `GET /sleep HTTP/1.1`
- wszystko inne → 404

To świadomie prymitywne, ale wystarczające do pokazania architektury serwera.

## Odpowiedź HTTP

Zarys odpowiedzi:

- status line,
- nagłówki,
- pusta linia,
- body.

W praktyce projekt ładuje gotowe pliki HTML i zwraca je jako treść odpowiedzi.

## Wersja jednowątkowa: problem

Single-threaded serwer przetwarza połączenia sekwencyjnie. Jeśli jeden request jest powolny, wszystkie następne czekają.

Książka pokazuje to przez endpoint `/sleep`, który robi:

```rust
std::thread::sleep(std::time::Duration::from_secs(5));
```

Efekt: szybkie requesty blokują się za jednym wolnym requestem. To dobrze pokazuje potrzebę współbieżności.

## Wersja pośrednia: nowy wątek per request

Pierwsze ulepszenie:

```rust
use std::thread;

for stream in listener.incoming() {
    let stream = stream.unwrap();

    thread::spawn(|| {
        handle_connection(stream);
    });
}
```

To pozwala obsługiwać requesty równolegle, ale ma poważny problem: bez limitu można stworzyć zbyt wiele wątków i przeciążyć system.

## Thread pool: idea

Docelowe rozwiązanie to pula wątków o stałym rozmiarze:

- z góry tworzysz określoną liczbę workerów,
- requesty zamieniasz na joby,
- joby trafiają do kolejki,
- workery pobierają je i wykonują.

To zwiększa throughput bez nieograniczonego mnożenia wątków.

## Docelowe API `ThreadPool`

W książce interfejs ma wyglądać mniej więcej tak:

```rust
let pool = ThreadPool::new(4);

for stream in listener.incoming() {
    let stream = stream.unwrap();

    pool.execute(|| {
        handle_connection(stream);
    });
}
```

To jest cel ergonomiczny: wywołanie ma przypominać `thread::spawn`, ale działać przez pulę pracowników.

## `ThreadPool::new`

Podstawowa walidacja:

```rust
pub fn new(size: usize) -> ThreadPool {
    assert!(size > 0);
    // ...
}
```

Rozdział wybiera `assert!`, czyli panic dla `size == 0`, zamiast `Result`, bo taki przypadek traktuje jako błąd użycia API przez programistę.

## `FnOnce` w jobach

`execute` przyjmuje domknięcie typu podobnego do tego, czego oczekuje `thread::spawn`:

```rust
pub fn execute<F>(&self, f: F)
where
    F: FnOnce() + Send + 'static,
{
    // ...
}
```

Znaczenie ograniczeń:

- `FnOnce` — job może zostać wykonany tylko raz,
- `Send` — domknięcie da się bezpiecznie przenieść do innego wątku,
- `'static` — closure nie opiera się na krótkotrwałych borrowach.

To jest bardzo ważna sygnatura i warto ją rozpoznawać.

## `Worker`

Zamiast trzymać same `JoinHandle`, thread pool trzyma workery:

```rust
struct Worker {
    id: usize,
    thread: thread::JoinHandle<()>,
}
```

Worker to cienka warstwa organizacyjna nad wątkiem, która daje sensowną jednostkę do debugowania i zarządzania.

## Kolejka jobów: kanał

Thread pool buduje kanał i trzyma sender, a workery współdzielą receiver.

Zarys:

```rust
use std::sync::mpsc;

let (sender, receiver) = mpsc::channel();
```

Później `execute` wysyła job do kolejki, a worker go odbiera i uruchamia.

## Alias `Job`

W książce job to alias na boxed domknięcie:

```rust
type Job = Box<dyn FnOnce() + Send + 'static>;
```

To klasyczne użycie:

- obiekt traitowy,
- boxed domknięcie,
- typ gotowy do wsadzenia do kanału i odpalenia przez worker.

## `Arc<Mutex<Receiver<Job>>>`

Problem: receiver nie daje się po prostu sklonować dla wielu workerów. Trzeba go współdzielić bezpiecznie między wątkami:

```rust
use std::sync::{Arc, Mutex};

let receiver = Arc::new(Mutex::new(receiver));
```

Każdy worker dostaje klona `Arc`, a `Mutex` gwarantuje, że tylko jeden worker naraz pobiera job z kanału.

To bardzo typowy wzorzec: `Arc<Mutex<T>>`.

## Wykonanie joba przez workera

Wątek workera robi mniej więcej to:

```rust
let job = receiver.lock().unwrap().recv().unwrap();
job();
```

Znaczenie:

- lock na receiverze,
- pobranie joba z kanału,
- wykonanie domknięcia.

Rozdział zwraca uwagę na subtelność scope’ów i lifetime’ów temporaries: zapis musi być tak ułożony, żeby mutex guard został zwolniony przed `job()`, inaczej worker trzymałby lock zbyt długo i dławił konkurencję.

## Dlaczego nie `while let` w prostszej formie

Pozornie kuszący zapis z `while let` może przypadkiem trzymać lock aż do końca bloku i przez to serializować pracę workerów. To dobra lekcja: przy `Mutex` znaczenie ma nie tylko *co* robisz, ale też *jak długo* żyje guard.

## Graceful shutdown

Samo działające wykonywanie jobów nie wystarcza. Serwer i pula wątków powinny umieć zakończyć się porządnie:

- przestać przyjmować nowe joby,
- pozwolić workerom dokończyć aktualną pracę,
- dołączyć wątki (`join`).

## `Drop` dla `ThreadPool`

Thread pool implementuje `Drop`, żeby posprzątać workery przy wychodzeniu ze scope.

Zarys:

```rust
impl Drop for ThreadPool {
    fn drop(&mut self) {
        for worker in self.workers.drain(..) {
            worker.thread.join().unwrap();
        }
    }
}
```

Książka pokazuje, że `drain(..)` jest wygodnym sposobem wyjęcia workerów z wektora i przekazania ownership `JoinHandle` do `join()`.

## Zamknięcie kanału jako sygnał stopu

Samo `join` nie wystarczy, bo workery siedzą w nieskończonej pętli `recv()`. Trzeba je poinformować, że więcej jobów nie będzie.

Strategia:

- jawnie zdropować `sender`,
- wtedy `recv()` zacznie zwracać błąd,
- worker rozpozna to jako sygnał końca i przerwie pętlę.

To bardzo elegancki wzorzec shutdownu oparty o semantykę kanału.

## Worker loop przy shutdownie

Kształt logiki końcowej:

```rust
match receiver.lock().unwrap().recv() {
    Ok(job) => {
        println!("Worker got a job; executing.");
        job();
    }
    Err(_) => {
        println!("Worker disconnected; shutting down.");
        break;
    }
}
```

To pozwala domknąć pulę bez brutalnego ubijania wątków.

## Co projekt naprawdę pokazuje

To nie jest produkcyjny web server. Najważniejsze lekcje są architektoniczne:

- prymitywy standard library wystarczają, żeby zrozumieć model działania serwera,
- pula wątków to nie magia, tylko sensowne połączenie wątków, kanału, ownership i `Drop`,
- granice odpowiedzialności API (`ThreadPool`, `Worker`, `Job`) mają znaczenie.

## Najważniejsze decyzje projektowe z rozdziału

| Problem | Rozwiązanie |
|---|---|
| sekwencyjna obsługa requestów | wielowątkowość |
| zbyt wiele wątków przy `spawn` per request | pula wątków o stałym rozmiarze |
| przekazywanie pracy workerom | kanał `mpsc` |
| współdzielenie jednego receivera | `Arc<Mutex<Receiver<Job>>>` |
| pojedyncze uruchamianie domknięcia | `FnOnce` |
| eleganckie zakończenie | zamknięcie kanału + `Drop` + `join` |

## Co zapamiętać

1. `TcpListener::bind` i `incoming()` wystarczają do zbudowania najprostszego serwera TCP/HTTP.
2. Jednowątkowy serwer łatwo blokuje się na wolnych requestach.
3. `thread::spawn` per request poprawia współbieżność, ale nie skaluje się bez limitu.
4. Thread pool rozwiązuje ten problem przez stałą liczbę workerów i kolejkę zadań.
5. Joby w puli są naturalnie modelowane jako `Box<dyn FnOnce() + Send + 'static>`.
6. Kanał `mpsc` dobrze nadaje się do dystrybucji pracy do workerów.
7. Współdzielony receiver wymaga `Arc<Mutex<...>>`.
8. `Drop` na `ThreadPool` może posłużyć do graceful shutdown, ale trzeba wcześniej zamknąć kanał, żeby workery wyszły z pętli.
9. To samo rozumowanie przydaje się później również przy analizie runtime’ów async, które często pod spodem także używają pul wątków i kolejek pracy.
