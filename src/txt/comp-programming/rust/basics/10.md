# 10

## Cel rozdziału

Rozdział 10 łączy trzy powiązane tematy:

- **generics** — usuwanie duplikacji przez parametry typu,
- **traits** — opisywanie wspólnego zachowania,
- **lifetimes** — opisywanie relacji ważności referencji.

To rdzeń „abstrakcji bez kosztu w runtime” w Ruście.

## Generics: po co

Najpierw warto pamiętać motywację: generics są naturalnym rozwinięciem zwykłego wyciągania funkcji. Zamiast tylko parametryzować wartości, parametryzujesz także typy.

## Generyczne funkcje

Schemat:

```rust
fn largest<T>(list: &[T]) -> &T {
    // ...
}
```

Parametr typu deklaruje się w `<>` między nazwą funkcji a listą parametrów.

W praktyce samo `T` często nie wystarcza — kod w ciele funkcji może wymagać, żeby `T` wspierał pewne operacje, np. porównywanie. Wtedy dochodzą trait bounds.

## Generyczne struktury

Przykład z jednym parametrem typu:

```rust
struct Point<T> {
    x: T,
    y: T,
}
```

Taki `Point<T>` wymaga, by `x` i `y` miały ten sam typ.

Jeśli typy mają się różnić:

```rust
struct Point<T, U> {
    x: T,
    y: U,
}
```

Wniosek praktyczny:

- jeden parametr typu = spójny typ w kilku miejscach,
- wiele parametrów = niezależność typów.

## Generyczne enumy

Najważniejsze przykłady ze standard library:

```rust
enum Option<T> {
    Some(T),
    None,
}
```

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

To właśnie dlatego `Option` i `Result` działają dla dowolnych typów danych i błędów.

## Generyczne metody i `impl`

Metody na typie generycznym też potrzebują deklaracji parametru typu przy `impl`:

```rust
struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn x(&self) -> &T {
        &self.x
    }
}
```

Można też pisać `impl` tylko dla konkretnego podstawienia typu:

```rust
impl Point<f32> {
    fn distance_from_origin(&self) -> f32 {
        (self.x.powi(2) + self.y.powi(2)).sqrt()
    }
}
```

To oznacza, że dana metoda istnieje tylko dla `Point<f32>`, nie dla wszystkich `Point<T>`.

## Różne generyki w typie i metodzie

Metoda może wprowadzać własne parametry typu niezależne od tych z definicji struktury. To ważne np. przy łączeniu danych z dwóch różnych obiektów generycznych.

## Koszt wykonania

Rozdział podkreśla, że cała ta elastyczność nie oznacza kary w runtime. Analiza i specjalizacja dzieją się na etapie kompilacji.

## Traits: wspólne zachowanie

Trait opisuje zestaw metod, które typ musi oferować.

Przykład:

```rust
pub trait Summary {
    fn summarize(&self) -> String;
}
```

Trait nie przechowuje danych; opisuje tylko zachowanie.

## Implementacja traitu

Implementacja wygląda tak:

```rust
pub struct NewsArticle {
    pub headline: String,
    pub location: String,
    pub author: String,
    pub content: String,
}

impl Summary for NewsArticle {
    fn summarize(&self) -> String {
        format!("{}, by {} ({})", self.headline, self.author, self.location)
    }
}
```

To jest analogiczne do metod, ale z `impl Trait for Type`.

## Orphan rule / coherence

Ważne ograniczenie:

- możesz zaimplementować trait dla typu tylko wtedy, gdy **trait albo typ** jest lokalny dla Twojego crate’a.

Nie wolno implementować zewnętrznego traitu dla zewnętrznego typu. To chroni ekosystem przed konfliktami implementacji.

## Domyślne implementacje w traitach

Trait może zawierać gotową implementację:

```rust
pub trait Summary {
    fn summarize(&self) -> String {
        String::from("(Read more...)")
    }
}
```

Typ implementujący trait może:

- użyć defaultu,
- albo nadpisać metodę własną implementacją.

Trait może też definiować metodę domyślną opartą o inną metodę wymaganą od implementora.

## Traits jako parametry

Najkrótsza forma:

```rust
pub fn notify(item: &impl Summary) {
    println!("Breaking news! {}", item.summarize());
}
```

To znaczy: funkcja przyjmuje dowolny typ implementujący `Summary`.

## Trait bounds

Równoważna forma jawna:

```rust
pub fn notify<T: Summary>(item: &T) {
    println!("Breaking news! {}", item.summarize());
}
```

To ważne rozróżnienie semantyczne:

- `&impl Summary` jest wygodne w prostych przypadkach,
- `T: Summary` daje większą kontrolę, np. gdy kilka parametrów ma mieć ten sam typ.

Przykład wymuszenia identycznego typu dla dwóch parametrów:

```rust
pub fn notify<T: Summary>(item1: &T, item2: &T) {
    // ...
}
```

## Wiele trait bounds

Można wymagać kilku traitów naraz:

```rust
use std::fmt::Display;

pub fn notify(item: &(impl Summary + Display)) {
    // ...
}
```

Albo w wersji z parametrem typu:

```rust
pub fn notify<T: Summary + Display>(item: &T) {
    // ...
}
```

## `where`

Przy większej liczbie ograniczeń czytelniejsze bywa `where`:

```rust
use std::fmt::{Debug, Display};

fn some_function<T, U>(t: &T, u: &U) -> i32
where
    T: Display + Clone,
    U: Clone + Debug,
{
    0
}
```

Semantyka ta sama, ale sygnatura jest mniej zatłoczona.

## Zwracanie `impl Trait`

Można też ukryć konkretny typ zwracany, o ile implementuje dany trait:

```rust
fn returns_summarizable() -> impl Summary {
    SocialPost {
        username: String::from("horse_ebooks"),
        content: String::from("of course, as you probably already know, people"),
        reply: false,
        repost: false,
    }
}
```

Ograniczenie: jedna taka funkcja musi zwracać jeden konkretny typ, nie „raz jeden, raz drugi”.

## Warunkowe implementacje

Można implementować metody albo traity tylko dla typów spełniających warunki.

Przykład:

```rust
use std::fmt::Display;

struct Pair<T> {
    x: T,
    y: T,
}

impl<T> Pair<T> {
    fn new(x: T, y: T) -> Self {
        Self { x, y }
    }
}

impl<T: Display + PartialOrd> Pair<T> {
    fn cmp_display(&self) {
        if self.x >= self.y {
            println!("The largest member is x = {}", self.x);
        } else {
            println!("The largest member is y = {}", self.y);
        }
    }
}
```

To oznacza: `cmp_display` istnieje tylko wtedy, gdy `T` można porównać i wypisać.

## Blanket implementations

Rust wspiera też implementacje „dla każdego typu, który spełnia trait”. Klasyczny przykład ze standard library:

```rust
impl<T: Display> ToString for T {
    // ...
}
```

Dlatego wszystko, co implementuje `Display`, dostaje też `to_string()`.

## Lifetimes: po co

Lifetimes to generyki nie o typach, tylko o **relacjach ważności referencji**. Nie zmieniają czasu życia danych — opisują go na tyle, by borrow checker mógł udowodnić bezpieczeństwo.

Główny cel: zapobieganie dangling references.

## Podstawowa intuicja

Każda referencja ma lifetime. Zwykle kompilator go wywnioskuje. Adnotacje są potrzebne tam, gdzie relacje między referencjami nie są oczywiste.

## Lifetime w funkcjach

Klasyczny przykład:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

To **nie znaczy**, że wszystko żyje dokładnie tyle samo. To znaczy: zwracana referencja jest ważna co najwyżej tak długo, jak wspólna część lifetime’ów argumentów.

Najważniejsze:

- adnotacja opisuje relację,
- nie wydłuża żadnego realnego czasu życia,
- borrow checker używa jej jako kontraktu funkcji.

## Ważna zasada dla zwracanych referencji

Jeśli funkcja zwraca referencję, jej lifetime musi być powiązany z lifetime’em któregoś wejściowego argumentu. Nie można legalnie zwrócić referencji do lokalnej wartości utworzonej w funkcji.

## Syntax lifetime annotations

Podstawowe formy:

```rust
&i32
&'a i32
&'a mut i32
```

Nazwy lifetime’ów:

- zaczynają się od apostrofu,
- zwykle są krótkie, np. `'a`, `'b`.

## Lifetimes w strukturach

Jeśli struktura przechowuje referencję, musi mieć lifetime parameter:

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}
```

To oznacza: instancja `ImportantExcerpt<'a>` nie może żyć dłużej niż referencja przechowywana w `part`.

## Lifetimes w metodach

Jeśli lifetime należy do typu struktury, deklarujesz go po `impl` i przy nazwie typu:

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}

impl<'a> ImportantExcerpt<'a> {
    fn level(&self) -> i32 {
        3
    }
}
```

Często w sygnaturach metod nie trzeba dopisywać lifetime’ów ręcznie, bo działają reguły elision.

## Lifetime elision rules

Rust ma trzy podstawowe reguły upraszczające zapis.

1. Każdy parametr będący referencją dostaje własny input lifetime.
2. Jeśli jest dokładnie jeden input lifetime, trafia też do wszystkich output lifetime’ów.
3. Jeśli jest wiele input lifetime’ów, ale jeden z parametrów to `&self` albo `&mut self`, to lifetime `self` trafia do outputów.

Dzięki temu takie funkcje nie wymagają jawnych adnotacji:

```rust
fn first_word(s: &str) -> &str {
    // ...
}
```

Ale `longest(x: &str, y: &str) -> &str` już wymaga jawnej adnotacji, bo po zastosowaniu reguł nadal pozostaje niejednoznaczność.

## `'static`

Specjalny lifetime `'static` oznacza referencję, która może żyć przez cały czas działania programu.

Przykład:

```rust
let s: &'static str = "I have a static lifetime.";
```

String literal ma `'static`, bo jego dane są zaszyte w binarce.

Ważna uwaga praktyczna: sugestia kompilatora, by dodać `'static`, często nie oznacza, że to dobre rozwiązanie. Bardzo często prawdziwy problem to zła relacja borrowów albo próba stworzenia dangling reference.

## Generics + traits + lifetimes razem

Wszystkie te mechanizmy mogą występować w jednej sygnaturze:

```rust
use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(
    x: &'a str,
    y: &'a str,
    ann: T,
) -> &'a str
where
    T: Display,
{
    println!("Announcement! {ann}");
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

To dobry mentalny model rozdziału 10: typy, zachowania i relacje ważności są wszystkimi różnymi warstwami jednego kontraktu API.

## Co zapamiętać

1. Generics usuwają duplikację przez parametryzację typów.
2. Sam generyczny typ zwykle wymaga trait bounds, jeśli kod chce wykonywać na nim konkretne operacje.
3. Traits opisują wspólne zachowanie typów i pełnią rolę kontraktów.
4. `impl Trait` jest wygodne w prostych sygnaturach, a jawne trait bounds i `where` są lepsze przy większej złożoności.
5. Można implementować metody i traity warunkowo, zależnie od trait bounds.
6. Lifetimes nie wydłużają życia referencji; opisują zależności między nimi.
7. Zwracana referencja musi być powiązana z którymś wejściowym borrowem, a nie z lokalną wartością utworzoną w funkcji.
8. Reguły lifetime elision eliminują dużą część boilerplate’u, ale nie usuwają rzeczywistej semantyki.
9. `'static` ma konkretne znaczenie i nie jest uniwersalnym „naprawiaczem” błędów borrow checkera.
