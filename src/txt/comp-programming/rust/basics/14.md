# 14

## Cel rozdziału

Rozdział 14 zbiera ważniejsze „operacyjne” elementy ekosystemu Cargo i crates.io:

- profile buildów,
- publikowanie crate’ów,
- dokumentację i doctesty,
- wygodne publiczne API przez `pub use`,
- workspace’y,
- `cargo install`,
- rozszerzanie Cargo własnymi subkomendami.

To nie jest rozdział o języku sensu stricto, tylko o praktyce pracy z projektami Rustowymi.

## Release profiles

Cargo ma dwa główne profile:

- `dev` — używany przez `cargo build`,
- `release` — używany przez `cargo build --release`.

Domyślnie:

- `dev` stawia na szybki czas kompilacji,
- `release` stawia na wydajność wynikowego kodu.

### Przykład konfiguracji

```toml
[profile.dev]
opt-level = 0

[profile.release]
opt-level = 3
```

`opt-level` steruje poziomem optymalizacji w zakresie `0..=3`.

### Własne nadpisanie

Jeśli chcesz np. trochę więcej optymalizacji także w developmencie:

```toml
[profile.dev]
opt-level = 1
```

Wniosek praktyczny:

- wyższa optymalizacja = wolniejszy build, szybszy binarny wynik,
- niższa optymalizacja = szybszy build, wolniejszy wynik.

## Dokumentacja crate’a

Rust ma dedykowane komentarze dokumentacyjne.

### `///` dla elementów publicznych

```rust
/// Adds one to the number given.
///
/// # Examples
///
/// ```
/// let arg = 5;
/// let answer = my_crate::add_one(arg);
///
/// assert_eq!(6, answer);
/// ```
pub fn add_one(x: i32) -> i32 {
    x + 1
}
```

To generuje HTML docs i opisuje *użycie* API, a nie jego implementację.

### `//!` dla kontenera

Komentarz `//!` dokumentuje element zawierający komentarz, zwykle cały crate albo moduł:

```rust
//! # My Crate
//!
//! `my_crate` is a collection of utilities...
```

Typowe miejsce: początek `src/lib.rs` albo pliku modułu.

## `cargo doc`

Budowanie dokumentacji:

```bash
cargo doc
```

Otwieranie od razu w przeglądarce:

```bash
cargo doc --open
```

Dokumentacja trafia do `target/doc`.

## Doctesty

Kod w blokach przykładów w komentarzach dokumentacyjnych jest uruchamiany przez `cargo test`.

To bardzo ważne: przykłady w dokumentacji nie są „martwe”, tylko testowane. Dzięki temu łatwiej utrzymać spójność między API a dokumentacją.

## Typowe sekcje dokumentacji

Rozdział wymienia częste nagłówki w doc comments:

- `# Examples`
- `# Panics`
- `# Errors`
- `# Safety`

To dobra checklista dla publicznego API.

## `pub use` i wygodne publiczne API

Wewnętrzna struktura crate’a nie zawsze jest wygodna dla użytkownika. Można ją odseparować od publicznego API przez re-export.

Przykład:

```rust
pub use crate::kinds::PrimaryColor;
pub use crate::kinds::SecondaryColor;
pub use crate::utils::mix;
```

Dzięki temu użytkownik może pisać krótsze i bardziej intuicyjne importy, bez poznawania całej wewnętrznej hierarchii modułów.

### Sens `pub use`

- zachowujesz własną organizację wewnętrzną,
- wystawiasz prostsze publiczne API,
- poprawiasz ergonomię i dokumentację dla użytkownika crate’a.

To istotny element projektowania bibliotek.

## Publikowanie na crates.io

### Konto i token

Przed publikacją trzeba:

1. założyć konto na crates.io,
2. pobrać API token,
3. zapisać go lokalnie:

```bash
cargo login
```

Token jest sekretem i nie wolno go upubliczniać.

### Minimalne metadane w `Cargo.toml`

Crate gotowy do publikacji potrzebuje m.in.:

```toml
[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"
```

Najważniejsze uwagi:

- nazwa crate’a na crates.io musi być unikalna,
- `description` i `license` są praktycznie obowiązkowe do publikacji,
- `license` używa identyfikatorów SPDX, np. `MIT`, `Apache-2.0`, `MIT OR Apache-2.0`.

Jeśli licencja nie ma identyfikatora SPDX, używa się `license-file`.

## `cargo publish`

Publikacja:

```bash
cargo publish
```

Ważna własność crates.io:

- opublikowana wersja jest trwała,
- nie można jej nadpisać,
- nie można jej zwyczajnie usunąć.

To wynika z roli crates.io jako trwałego archiwum zależności.

## Nowe wersje i semver

Nowe wydanie = zmiana `version` w `Cargo.toml` zgodnie z zasadami Semantic Versioning i ponowne `cargo publish`.

## `cargo yank`

Jeśli wersja jest zła, ale nie chcesz jej usuwać (bo i tak się nie da), możesz ją yanknąć:

```bash
cargo yank --vers 1.0.1
```

Cofnięcie:

```bash
cargo yank --vers 1.0.1 --undo
```

Znaczenie yanka:

- nowe projekty nie dostaną tej wersji,
- istniejące projekty z już zapisanym `Cargo.lock` nadal działają.

Yank nie usuwa kodu z rejestru.

## Cargo workspaces

Workspace to zestaw powiązanych package’y rozwijanych razem, współdzielących:

- jeden `Cargo.lock`,
- jeden katalog `target/`.

### Minimalny workspace

Top-level `Cargo.toml`:

```toml
[workspace]
resolver = "3"
members = ["adder", "add_one"]
```

W tym pliku nie ma `[package]`, tylko konfiguracja workspace’a.

### Kluczowe własności

- każdy member pozostaje własnym package’em / crate’em,
- build artifacts trafiają do wspólnego `target/`,
- zależności wersjonują się wspólnie przez jeden `Cargo.lock`.

To upraszcza rozwój wielocrate’owych projektów i ogranicza niepotrzebne przebudowy.

## Zależności wewnątrz workspace’a

Cargo nie zakłada automatycznie zależności między memberami. Trzeba je zadeklarować jawnie, zwykle przez path dependency.

Przykład w `adder/Cargo.toml`:

```toml
[dependencies]
add_one = { path = "../add_one" }
```

## Uruchamianie paczki w workspace

Jeśli workspace ma kilka package’y, można wskazać, który uruchomić:

```bash
cargo run -p adder
```

## Zewnętrzne zależności w workspace

Wspólny `Cargo.lock` powoduje, że membery używają zgodnych wersji zależności. To pomaga utrzymać kompatybilność między crate’ami workspace’a.

## `cargo install`

`cargo install` służy do lokalnej instalacji binarnych crate’ów:

```bash
cargo install ripgrep
```

Ważne:

- działa tylko dla crate’ów z binary targetem,
- nie służy do instalacji bibliotek do użycia w `Cargo.toml`,
- instalowane binarki trafiają zwykle do `~/.cargo/bin`.

Jeśli ten katalog jest w `PATH`, komenda staje się normalnie uruchamialna z shella.

## Rozszerzanie Cargo własnymi subkomendami

Cargo rozpoznaje binarki nazwane `cargo-*` jako własne subkomendy. Jeśli masz coś w `PATH` o nazwie np. `cargo-something`, możesz uruchomić:

```bash
cargo something
```

To pozwala rozszerzać Cargo bez modyfikowania samego Cargo.

### Praktyczna implikacja

Po `cargo install` takiego narzędzia dostajesz komendę, która zachowuje się jak natywna część Cargo.

## Najważniejsze decyzje praktyczne z rozdziału

| Problem | Narzędzie |
|---|---|
| chcesz inny kompromis build speed / runtime speed | profile w `Cargo.toml` |
| chcesz opublikować bibliotekę | `cargo publish` + metadane |
| chcesz wygodniejsze API niż struktura wewnętrzna | `pub use` |
| chcesz utrzymać wiele crate’ów razem | workspace |
| chcesz zainstalować narzędzie CLI | `cargo install` |
| chcesz własną subkomendę Cargo | binarka `cargo-*` |

## Co zapamiętać

1. `dev` i `release` to odrębne profile kompilacji z innymi kompromisami.
2. Dokumentacja Rusta opiera się na `///` i `//!`, a `cargo doc` generuje ją automatycznie.
3. Przykłady w doc comments są wykonywane jako doctesty przez `cargo test`.
4. `pub use` pozwala wystawić prostsze publiczne API niż wynika to z organizacji wewnętrznej crate’a.
5. Publikacja na crates.io wymaga sensownych metadanych i jest trwała per wersja.
6. `cargo yank` wycofuje wersję z nowych zależności, ale jej nie usuwa.
7. Workspace współdzieli `Cargo.lock` i `target/`, co ułatwia rozwój wielocrate’owych projektów.
8. `cargo install` służy do binarnych narzędzi, nie do zwykłych zależności bibliotecznych.
9. Binarki `cargo-*` rozszerzają Cargo o własne subkomendy.
