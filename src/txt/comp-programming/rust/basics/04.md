# 04

## Cel rozdziału

Rozdział 4 wprowadza ownership — centralny mechanizm Rusta do zarządzania pamięcią bez garbage collectora. Z nim powiązane są borrowing, referencje i slice’y. To fundament późniejszych rozdziałów.

## Trzy reguły ownership

1. Każda wartość w Ruście ma właściciela.
2. W danym momencie właściciel może być tylko jeden.
3. Gdy właściciel wychodzi poza zakres, wartość zostaje `drop`nięta.

To właśnie te reguły pozwalają kompilatorowi egzekwować bezpieczeństwo pamięci na etapie kompilacji.

## Stack vs heap

Rozdział używa klasycznego rozróżnienia:

- **stack**: dane o znanym, stałym rozmiarze; szybkie push/pop,
- **heap**: dane o rozmiarze dynamicznym; wymaga alokacji i śledzenia adresu przez wskaźnik.

Praktyczny sens dla Rusta:

- proste typy skalarne zwykle żyją w całości na stacku,
- typy takie jak `String` trzymają na stacku metadane, a treść na heapie,
- ownership przede wszystkim porządkuje cykl życia danych na heapie.

## Zakres i `drop`

Wartość jest ważna od momentu wejścia do scope do jego końca. Dla typów zarządzających pamięcią Rust automatycznie wywołuje `drop` przy wyjściu ze scope.

```rust
let s = String::from("hello");
```

W przeciwieństwie do string literal, `String`:

- alokuje pamięć na heapie,
- może się zmieniać,
- jest automatycznie zwalniany, gdy właściciel wychodzi ze scope.

## `String` i mutowalność

`String` służy do mutowalnego, dynamicznego tekstu:

```rust
let mut s = String::from("hello");
s.push_str(", world");
```

String literal (`"hello"`) jest niemutowalny i osadzony w binarce; `String` ma bardziej kosztowną, ale elastyczną reprezentację.

## Move

Dla typów heapowych przypisanie zwykle oznacza **move**, a nie kopiowanie danych użytkowych:

```rust
let s1 = String::from("hello");
let s2 = s1;
```

Po takim przypisaniu:

- kopiowane są metadane `String` ze stacka,
- dane na heapie nie są automatycznie duplikowane,
- `s1` przestaje być ważne,
- tylko `s2` pozostaje właścicielem.

To zapobiega problemowi double free.

### Co zapamiętać

- Rust nie robi automatycznie deep copy dla `String` i podobnych typów,
- automatyczne kopiowanie ma być tanie,
- użycie wartości po move jest błędem kompilacji.

## `clone`

Jeśli potrzebujesz prawdziwej kopii danych na heapie, używasz `clone`:

```rust
let s1 = String::from("hello");
let s2 = s1.clone();
```

Tu obie zmienne mają własne, niezależne dane. `clone()` jest jawne, więc od razu sygnalizuje potencjalny koszt.

## `Copy`

Dla typów prostych, w pełni stackowych, przypisanie tworzy zwykłą kopię:

```rust
let x = 5;
let y = x;
```

`x` pozostaje ważne, bo typ implementuje `Copy`.

Typowo `Copy` mają:

- liczby całkowite,
- `bool`,
- liczby zmiennoprzecinkowe,
- `char`,
- tuple złożone wyłącznie z typów `Copy`.

Typ wymagający `Drop` nie może jednocześnie być `Copy`.

## Ownership a funkcje

Przekazanie argumentu do funkcji działa tak samo jak przypisanie: wartość jest albo kopiowana, albo przenoszona.

```rust
fn takes_ownership(some_string: String) {
    println!("{some_string}");
}

fn makes_copy(some_integer: i32) {
    println!("{some_integer}");
}
```

Wywołanie z `String` zwykle przenosi ownership do funkcji. Wywołanie z `i32` kopiuje wartość.

## Zwracanie wartości

Zwracanie wartości także może przenosić ownership:

```rust
fn gives_ownership() -> String {
    String::from("yours")
}

fn takes_and_gives_back(a_string: String) -> String {
    a_string
}
```

To działa, ale bywa niewygodne: funkcja musi oddać wartość z powrotem, jeśli wywołujący nadal ma jej używać. Właśnie ten problem rozwiązuje borrowing.

## Referencje i borrowing

Referencja pozwala używać wartości bez przejmowania ownership:

```rust
fn calculate_length(s: &String) -> usize {
    s.len()
}

let s1 = String::from("hello");
let len = calculate_length(&s1);
```

Najważniejsze:

- `&s1` tworzy referencję,
- funkcja dostaje dostęp do danych, ale nie staje się właścicielem,
- po wywołaniu nadal możesz używać `s1`.

Borrowing oznacza więc „pożyczam dostęp, ale nie własność”.

## Mutable references

Domyślna referencja nie pozwala modyfikować danych. Do mutacji potrzebna jest mutowalna referencja:

```rust
fn change(some_string: &mut String) {
    some_string.push_str(", world");
}

let mut s = String::from("hello");
change(&mut s);
```

To jest jawny kontrakt: funkcja może zmieniać pożyczoną wartość.

## Reguły borrowingu

Kluczowa reguła:

- albo możesz mieć **dowolnie wiele immutable references**,
- albo **jedną mutable reference**,
- ale nie jednocześnie obu rodzajów w nachodzących zakresach użycia.

Nie wolno więc robić tego równolegle:

- dwóch aktywnych `&mut` do tej samej wartości,
- `&` i `&mut` do tej samej wartości w tym samym czasie.

Powód: Rust zapobiega data races już na etapie kompilacji.

### Ważny szczegół praktyczny

Zasięg referencji liczy się do jej **ostatniego użycia**, nie tylko do końca bloku. Dzięki temu kod może kompilować się wtedy, gdy immutable borrow skończył się logicznie przed utworzeniem mutable borrow.

## Dangling references

Rust nie pozwala zwrócić referencji do wartości, która przestanie istnieć:

```rust
fn dangle() -> String {
    let s = String::from("hello");
    s
}
```

Poprawnym rozwiązaniem jest zwrócenie samej wartości, a nie referencji do lokalnej zmiennej. Kompilator blokuje dangling references zanim kod się uruchomi.

## Slice’y

Slice to referencja do spójnego fragmentu kolekcji. Nie ma ownership.

## String slice

Najczęściej spotykany przypadek to `&str`:

```rust
let s = String::from("hello world");

let hello = &s[0..5];
let world = &s[6..11];
```

Skróty składni:

```rust
let slice = &s[..2];
let slice = &s[3..];
let slice = &s[..];
```

Zakres ma postać `[start..end]`, gdzie `end` jest granicą wyłączoną.

### Ograniczenie UTF-8

Indeksy slice’ów tekstowych muszą wypadać na poprawnych granicach znaków UTF-8. Cięcie w środku znaku wielobajtowego kończy program błędem.

## `first_word` i przewaga slice’ów

Rozdział pokazuje, że zwracanie samego indeksu jest kruche, bo nie jest powiązane z aktualnym stanem stringa. Lepsze API zwraca slice:

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return &s[0..i];
        }
    }

    &s[..]
}
```

Zalety:

- wynik jest powiązany z oryginalnymi danymi,
- kompilator pilnuje ważności referencji,
- API na `&str` jest bardziej ogólne niż na `&String`.

## String literals jako slice’y

String literal ma typ `&str`:

```rust
let s = "Hello, world!";
```

To immutable slice wskazujący na dane osadzone w binarce.

## Slice tablic

Mechanizm slice’ów nie dotyczy tylko stringów:

```rust
let a = [1, 2, 3, 4, 5];
let slice = &a[1..3];

assert_eq!(slice, &[2, 3]);
```

Typ takiego slice’a to np. `&[i32]`.

## Co zapamiętać

1. Ownership zarządza głównie danymi heapowymi i eliminuje potrzebę ręcznego `free` oraz garbage collectora.
2. `String` przy przypisaniu zwykle się przenosi, a nie kopiuje.
3. `clone()` robi jawną, głęboką kopię danych.
4. Typy `Copy` zachowują się jak tanie kopie i nie tracą ważności po przypisaniu.
5. Referencje pozwalają używać danych bez przejmowania ownership.
6. Reguła borrowingu brzmi praktycznie: wiele `&` albo jedno `&mut`.
7. Rust blokuje dangling references i część klas błędów pamięci jeszcze przed uruchomieniem programu.
8. Slice’y (`&str`, `&[T]`) pozwalają bezpiecznie wskazywać fragmenty danych bez kopiowania.
9. Sygnatury na `&str` są zwykle lepsze niż na `&String`, bo są bardziej ogólne.
