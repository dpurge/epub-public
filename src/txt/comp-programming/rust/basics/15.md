# 15

## Cel rozdziału

Rozdział 15 wprowadza standardowe smart pointers i kilka ważnych wzorców pamięciowych w Ruście:

- `Box<T>`
- `Deref`
- `Drop`
- `Rc<T>`
- `RefCell<T>`
- `Weak<T>`

To rozdział o bardziej zaawansowanym zarządzaniu własnością i dostępem do danych, zwłaszcza wtedy, gdy zwykłe referencje i zwykła wyłączna własność nie wystarczają.

## Smart pointer: czym jest

Referencja `&T` to najprostszy wskaźnik: tylko wskazuje na dane i niczego nie „wie” ponad to.

Smart pointer to zwykle struktura, która:

- zachowuje się jak wskaźnik,
- ale przechowuje dodatkowe metadane,
- i implementuje dodatkowe zachowania.

W Ruście smart pointery często **są właścicielami** danych, a nie tylko pożyczkami.

Najczęściej opierają się na implementacji traitów:

- `Deref` — żeby zachowywać się jak referencje,
- `Drop` — żeby wykonywać kod przy sprzątaniu.

## `Box<T>`

`Box<T>` to najprostszy smart pointer: pozwala umieścić wartość na heapie.

```rust
let b = Box::new(5);
println!("b = {b}");
```

Na stacku zostaje sam wskaźnik, a wartość trafia na heap.

### Główne przypadki użycia `Box<T>`

1. typ o rozmiarze nieznanym kompilatorowi wprost,
2. duża wartość, którą chcesz przenosić tanio przez przenoszenie wskaźnika,
3. chcesz posiadać coś przez abstrakcję, a nie przez konkretny typ (ważne później przy trait objects).

## Rekurencyjne typy i `Box<T>`

Klasyczny przypadek: lista rekurencyjna.

Bez `Box` to się nie kompiluje, bo typ miałby nieskończony rozmiar. Z `Box`:

```rust
enum List {
    Cons(i32, Box<List>),
    Nil,
}

use List::{Cons, Nil};

let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
```

Powód, dla którego to działa:

- `Box<T>` ma znany, stały rozmiar (rozmiar wskaźnika),
- więc rekurencja jest „przerwana” przez indirection.

## `Deref`

Trait `Deref` pozwala własnemu typowi zachowywać się jak referencja przy użyciu operatora `*`.

Przykład własnego smart pointera:

```rust
use std::ops::Deref;

struct MyBox<T>(T);

impl<T> MyBox<T> {
    fn new(x: T) -> MyBox<T> {
        MyBox(x)
    }
}

impl<T> Deref for MyBox<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &self.0
    }
}
```

Dzięki temu:

```rust
let x = 5;
let y = MyBox::new(x);

assert_eq!(5, *y);
```

Semantycznie `*y` rozwija się do czegoś w rodzaju `*(y.deref())`.

## Deref coercions

Rust potrafi automatycznie przekształcać referencje do typów implementujących `Deref` do oczekiwanego typu referencji w wywołaniach funkcji i metod.

Przykład:

```rust
fn hello(name: &str) {
    println!("Hello, {name}!");
}

let m = MyBox::new(String::from("Rust"));
hello(&m);
```

Dlaczego to działa:

- `&MyBox<String>` → `&String` przez `Deref`,
- `&String` → `&str` przez `Deref` standardowego `String`.

To istotnie poprawia ergonomię API.

## `Drop`

Trait `Drop` pozwala uruchomić kod sprzątający, gdy wartość wychodzi ze scope.

Przykład:

```rust
struct CustomSmartPointer {
    data: String,
}

impl Drop for CustomSmartPointer {
    fn drop(&mut self) {
        println!("Dropping CustomSmartPointer with data `{}`!", self.data);
    }
}
```

Rust wywołuje `drop` automatycznie. Nie trzeba pamiętać o ręcznym sprzątaniu zasobów.

### Kolejność dropowania

Wartości są dropowane w odwrotnej kolejności do tworzenia.

### Wczesne dropowanie

Nie wolno ręcznie wołać metody `Drop::drop`. Zamiast tego używa się funkcji ze standard library:

```rust
let c = CustomSmartPointer {
    data: String::from("my stuff"),
};

std::mem::drop(c);
```

To przydaje się np. gdy chcesz wcześnie zwolnić lock lub inny zasób.

## `Rc<T>`

`Rc<T>` (_reference counted_) pozwala na **współdzieloną własność** danych w kodzie jednowątkowym.

To rozwiązanie na sytuacje, gdzie nie da się wskazać jednego właściciela na etapie kompilacji.

### Podstawowy wzorzec

```rust
use std::rc::Rc;

let a = Rc::new(String::from("shared"));
let b = Rc::clone(&a);
let c = Rc::clone(&a);
```

Tu `a`, `b` i `c` współdzielą własność tej samej wartości.

### Dlaczego `Rc::clone`, a nie zwykłe `clone`

`Rc::clone(&a)`:

- nie robi deep copy danych,
- tylko zwiększa licznik referencji.

To rozróżnienie jest ważne semantycznie i wydajnościowo.

### Licznik referencji

Można go podejrzeć:

```rust
println!("count = {}", Rc::strong_count(&a));
```

Wartość zostaje zwolniona dopiero, gdy `strong_count` spadnie do `0`.

### Ograniczenie `Rc<T>`

`Rc<T>` jest tylko do single-threaded code. Do wielowątkowości używa się innych typów (rozdział 16).

## `RefCell<T>` i interior mutability

`RefCell<T>` pozwala mutować dane nawet wtedy, gdy zewnętrzna wartość wygląda na niemutowalną. To wzorzec **interior mutability**.

Najważniejsza różnica względem zwykłych referencji:

- zwykłe borrow rules są sprawdzane w compile time,
- `RefCell<T>` sprawdza je w runtime.

Jeśli złamiesz reguły borrowingu, program spanikuje.

### API

Zamiast `&` i `&mut` używasz:

```rust
borrow()
borrow_mut()
```

Przykład:

```rust
use std::cell::RefCell;

let x = RefCell::new(vec![1, 2, 3]);
x.borrow_mut().push(4);
```

### Kiedy to ma sens

Gdy wiesz, że kod jest logicznie poprawny, ale kompilator nie potrafi tego łatwo udowodnić. `RefCell<T>` daje elastyczność kosztem runtime checks.

## `Rc<RefCell<T>>`

To bardzo częste połączenie:

- `Rc<T>` daje współdzieloną własność,
- `RefCell<T>` daje mutowalność wnętrza.

Czyli: wiele miejsc może mieć dostęp do tego samego obiektu i móc go mutować.

To bardzo użyteczne, ale też łatwo wprowadza bardziej złożone zależności i ryzyko cykli referencji.

## Mock objects i `RefCell<T>`

Rozdział pokazuje praktyczny przykład: testowy `MockMessenger`, który musi modyfikować listę wysłanych wiadomości, mimo że trait wymaga `&self`.

Wzorzec:

```rust
use std::cell::RefCell;

struct MockMessenger {
    sent_messages: RefCell<Vec<String>>,
}

impl MockMessenger {
    fn new() -> MockMessenger {
        MockMessenger {
            sent_messages: RefCell::new(vec![]),
        }
    }
}
```

A potem w metodzie:

```rust
self.sent_messages.borrow_mut().push(String::from(message));
```

To klasyczny przypadek, gdzie interior mutability jest bardzo praktyczne.

## Cykle referencji

Rust gwarantuje memory safety, ale **nie gwarantuje braku wycieków pamięci**. Można stworzyć memory leak przez cykl `Rc<T>`.

Jeśli dwa obiekty trzymają do siebie wzajemnie silne referencje, ich `strong_count` nigdy nie spadnie do zera.

To jest logiczny błąd programu, nie błąd bezpieczeństwa pamięci.

## `Weak<T>`

Aby unikać cykli, używa się `Weak<T>`.

Tworzenie weak reference:

```rust
use std::rc::{Rc, Weak};

let strong = Rc::new(5);
let weak: Weak<i32> = Rc::downgrade(&strong);
```

Różnica:

- `Rc<T>` zwiększa `strong_count` i współdzieli ownership,
- `Weak<T>` zwiększa tylko `weak_count` i **nie** współdzieli ownership.

### `upgrade`

Ponieważ `Weak<T>` nie gwarantuje istnienia wartości, trzeba go podnieść jawnie:

```rust
if let Some(value) = weak.upgrade() {
    println!("value = {value}");
}
```

`upgrade()` zwraca `Option<Rc<T>>`:

- `Some(...)`, jeśli wartość jeszcze istnieje,
- `None`, jeśli została już dropnięta.

## Drzewo parent/children: typowy wzorzec

Dla relacji drzewiastych sensowny model jest taki:

- parent **posiada** children → `Rc<Node>` w dzieciach kolekcji,
- child tylko **wskazuje** parent → `Weak<Node>`.

Schemat z rozdziału:

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}
```

To pozwala:

- parentowi posiadać dzieci,
- dziecku znać parenta,
- ale bez tworzenia cyklu ownership.

## Kiedy który typ

| Typ | Własność | Mutowalność | Sprawdzanie borrowów |
|---|---|---|---|
| `Box<T>` | pojedyncza | zwykła | compile time |
| `Rc<T>` | współdzielona | tylko przez immutable access | compile time |
| `RefCell<T>` | pojedyncza | interior mutability | runtime |
| `Rc<RefCell<T>>` | współdzielona | interior mutability | runtime |
| `Weak<T>` | brak ownership | n/a | n/a |

## Co zapamiętać

1. Smart pointer w Ruście to zwykle typ posiadający dane i implementujący dodatkowe zachowania, np. `Deref` i `Drop`.
2. `Box<T>` służy głównie do alokacji na heapie i do typów rekurencyjnych o znanym rozmiarze wskaźnika.
3. `Deref` pozwala własnym typom zachowywać się jak referencje, a deref coercions poprawiają ergonomię API.
4. `Drop` automatyzuje sprzątanie zasobów; do wczesnego zwolnienia używa się `std::mem::drop`.
5. `Rc<T>` daje współdzieloną własność w kodzie jednowątkowym.
6. `RefCell<T>` przesuwa sprawdzanie borrow rules z czasu kompilacji do czasu działania i umożliwia interior mutability.
7. `Rc<RefCell<T>>` jest potężne, ale łatwo prowadzi do bardziej skomplikowanych zależności.
8. Cykle `Rc<T>` mogą powodować memory leak, mimo że program pozostaje memory-safe.
9. `Weak<T>` służy do relacji nie-właścicielskich i jest podstawowym narzędziem do rozbijania cykli referencji.
