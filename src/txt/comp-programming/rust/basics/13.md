# 13

## Cel rozdziału

Rozdział 13 wprowadza dwa filary idiomatycznego Rusta w stylu funkcyjnym:

- **domknięcia (closures)**
- **iteratory (iterators)**

oraz pokazuje, że te abstrakcje nie kosztują wydajnościowo tyle, ile intuicyjnie mogłoby się wydawać.

## Closures: czym są

Closure to anonimowa funkcja, którą można:

- przypisać do zmiennej,
- przekazać jako argument,
- wykonać później,
- a dodatkowo może przechwytywać wartości z otoczenia.

Podstawowy przykład:

```rust
let add_one = |x| x + 1;
```

To wygląda jak funkcja, ale closure może używać danych spoza swojej listy parametrów.

## Składnia i inferencja typów

Pełna forma:

```rust
let add_one = |x: u32| -> u32 { x + 1 };
```

Krótsza, najczęstsza forma:

```rust
let add_one = |x| x + 1;
```

Rust zwykle inferuje typy parametrów i wyników domknięcia. Jednak po pierwszym użyciu typy domknięcia „zatrzaskują się” na konkretnym typie.

To znaczy: domknięcie nie jest „polimorficzne na żądanie” jak funkcja generyczna. Jeśli najpierw użyjesz go z `String`, to potem nie użyjesz go z `i32` bez błędu typów.

## Capture otoczenia

Najważniejsza różnica względem zwykłych funkcji: domknięcie może przechwycić dane z zakresu, w którym zostało zdefiniowane.

Przykład:

```rust
let list = vec![1, 2, 3];

let only_borrows = || println!("From closure: {list:?}");

only_borrows();
```

Tu domknięcie korzysta z `list`, mimo że `list` nie jest jego parametrem.

## Sposoby przechwytywania

Domknięcie może przechwycić dane z otoczenia analogicznie do sposobów przekazywania parametrów do funkcji:

- przez immutable borrow,
- przez mutable borrow,
- przez move (przejęcie ownership).

Rust wybiera minimalny potrzebny sposób na podstawie tego, co closure robi z daną wartością.

### Immutable borrow

Jeśli domknięcie tylko czyta:

```rust
let list = vec![1, 2, 3];
let print = || println!("{list:?}");
```

### Mutable borrow

Jeśli domknięcie mutuje:

```rust
let mut list = vec![1, 2, 3];
let mut borrows_mutably = || list.push(7);

borrows_mutably();
```

### `move`

Jeśli chcesz wymusić przejęcie ownership:

```rust
let list = vec![1, 2, 3];
let takes_ownership = move || println!("{list:?}");
```

Najczęstszy praktyczny przypadek: przekazanie domknięcia do nowego wątku.

## `Fn`, `FnMut`, `FnOnce`

To trzy podstawowe traity opisujące, *jak* domknięcie obchodzi się z przechwyconym środowiskiem.

| Trait | Znaczenie |
|---|---|
| `FnOnce` | closure może zostać wywołane co najmniej raz; może skonsumować przechwycone wartości |
| `FnMut` | closure może być wołane wielokrotnie, ale może mutować przechwycone środowisko |
| `Fn` | closure może być wołane wielokrotnie i nie mutuje ani nie konsumuje środowiska |

Zależność jest „addytywna”: każde domknięcie implementuje przynajmniej `FnOnce`, a bardziej restrykcyjne zachowania dają też `FnMut` i `Fn`.

### Praktyczna intuicja

- jeśli closure coś **wynosi** ze środowiska → zwykle tylko `FnOnce`,
- jeśli closure tylko **mutuje** środowisko → `FnMut`,
- jeśli closure tylko **czyta** środowisko albo nic nie przechwytuje → `Fn`.

## Dlaczego to ma znaczenie

API biblioteki często określa, jakiego domknięcia oczekuje. Przykład z rozdziału: `Option::unwrap_or_else` przyjmuje `FnOnce`, bo domknięcie zostanie wywołane co najwyżej raz.

Z kolei np. `sort_by_key` wymaga domknięcia wywoływanego wielokrotnie, więc nie przyjmie domknięcia, które konsumuje środowisko przy pierwszym wywołaniu.

## Closures jako parametry bibliotecznych helperów

Ważny wzorzec z rozdziału:

```rust
user_preference.unwrap_or_else(|| self.most_stocked())
```

`unwrap_or_else`:

- jeśli `Option` ma `Some`, zwraca wartość,
- jeśli ma `None`, odpala closure i bierze jego wynik.

Tu domknięcie przechwytuje `self` i pozwala wstrzyknąć logikę „wyznacz domyślną wartość dopiero wtedy, gdy będzie potrzebna”.

## Iteratory: czym są

Iterator to obiekt odpowiedzialny za przechodzenie po sekwencji elementów i wiedzę, kiedy sekwencja się kończy.

Najważniejsza cecha: **iteratory w Ruście są lazy**. Samo ich utworzenie nic jeszcze nie robi.

```rust
let v1 = vec![1, 2, 3];
let v1_iter = v1.iter();
```

Ten kod jeszcze nie przetwarza elementów.

## `Iterator` trait i `next`

Sercem iteratora jest metoda `next`:

```rust
fn next(&mut self) -> Option<Self::Item>
```

Każde wywołanie:

- zwraca `Some(item)`, jeśli element jeszcze istnieje,
- zwraca `None`, gdy iterator się skończy.

Przykład:

```rust
let v1 = vec![1, 2, 3];
let mut v1_iter = v1.iter();

assert_eq!(v1_iter.next(), Some(&1));
assert_eq!(v1_iter.next(), Some(&2));
assert_eq!(v1_iter.next(), Some(&3));
assert_eq!(v1_iter.next(), None);
```

`next` wymaga `&mut self`, bo przesuwa stan iteratora do przodu.

## `iter`, `into_iter`, `iter_mut`

Trzy najważniejsze sposoby wejścia w iterację:

| Metoda | Co zwraca |
|---|---|
| `iter()` | iterator po `&T` |
| `into_iter()` | iterator po `T` z przejęciem ownership |
| `iter_mut()` | iterator po `&mut T` |

Przykłady:

```rust
let v = vec![1, 2, 3];
for x in v.iter() {
    println!("{x}");
}
```

```rust
let v = vec![1, 2, 3];
for x in v.into_iter() {
    println!("{x}");
}
```

```rust
let mut v = vec![1, 2, 3];
for x in v.iter_mut() {
    *x += 1;
}
```

## Consumers i adapters

Rozdział rozdziela dwie klasy metod iteratorów.

### Consuming adapters

Zużywają iterator i dają wynik końcowy.

Przykład:

```rust
let v1 = vec![1, 2, 3];
let total: i32 = v1.iter().sum();
```

`sum()` konsumuje iterator, więc po tym zwykle nie da się go dalej używać.

### Iterator adapters

Biorą iterator i zwracają nowy iterator.

Przykład:

```rust
let v1 = vec![1, 2, 3];
let v2: Vec<_> = v1.iter().map(|x| x + 1).collect();
```

`map()` sam nic nie robi, dopóki coś nie skonsumuje wyniku, np. `collect()`.

## Najczęstsze metody iteratorowe

### `sum`

```rust
let v1 = vec![1, 2, 3];
let total: i32 = v1.iter().sum();
```

### `map`

```rust
let v1 = vec![1, 2, 3];
let v2: Vec<_> = v1.iter().map(|x| x + 1).collect();
```

### `filter`

```rust
let shoes = vec![
    Shoe { size: 10, style: String::from("sneaker") },
    Shoe { size: 13, style: String::from("sandal") },
    Shoe { size: 10, style: String::from("boot") },
];

let shoe_size = 10;
let in_my_size: Vec<_> = shoes.into_iter()
    .filter(|s| s.size == shoe_size)
    .collect();
```

Tu domknięcie przechwytuje `shoe_size` z otoczenia.

### `collect`

`collect()` konsumuje iterator i buduje kolekcję wynikową. Często wymaga doprecyzowania typu docelowego, np. `Vec<_>`.

## Leniwość iteratorów

To częste źródło zaskoczeń:

```rust
let v1 = vec![1, 2, 3];
v1.iter().map(|x| x + 1);
```

To nic nie zrobi, bo wynik `map` nie został skonsumowany. Trzeba dodać np. `collect`, `sum`, `for_each` albo użyć iteratora w `for`.

## Refaktoryzacja `minigrep`

Rozdział wraca do projektu z rozdziału 12 i pokazuje, że iteratorowy styl upraszcza kod.

### `Config::build` bez zbędnych `clone`

Zamiast zbierać argumenty do `Vec<String>` i potem klonować, można przekazać iterator bezpośrednio:

```rust
use std::env;

let config = Config::build(env::args()).unwrap_or_else(|err| {
    eprintln!("Problem parsing arguments: {err}");
    std::process::exit(1);
});
```

A sygnatura:

```rust
impl Config {
    pub fn build(
        mut args: impl Iterator<Item = String>,
    ) -> Result<Config, &'static str> {
        args.next();

        let query = match args.next() {
            Some(arg) => arg,
            None => return Err("Didn't get a query string"),
        };

        let file_path = match args.next() {
            Some(arg) => arg,
            None => return Err("Didn't get a file path"),
        };

        Ok(Config { query, file_path, ignore_case: false })
    }
}
```

Zysk:

- mniej pośrednich struktur,
- brak niepotrzebnych `clone`,
- jaśniejsza semantyka „zużyj argumenty po kolei”.

### `search` w stylu iteratorowym

Imperatywnie wersja miała mutowalny `results` i pętlę `for`. Iteratorowa wersja:

```rust
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    contents
        .lines()
        .filter(|line| line.contains(query))
        .collect()
}
```

To samo znaczenie, ale:

- mniej mutowalnego stanu,
- bardziej deklaratywny zapis,
- czytelniej widać wysokopoziomowy cel: „weź linie, odfiltruj, zbierz”.

## Pętle vs iteratory

Rozdział wyraźnie mówi: większość Rustacean preferuje iteratory, gdy pasują do problemu, bo lepiej eksponują *intencję* kodu i eliminują boilerplate sterowania pętlą.

Nie znaczy to, że zwykłe pętle są złe; po prostu iteratorowy styl jest zwykle bardziej idiomatyczny i composable.

## Wydajność

Kluczowy wniosek rozdziału: iteratory i domknięcia są **zero-cost abstractions**.

Benchmark z książki pokazał bardzo zbliżoną wydajność między ręczną pętlą a wersją iteratorową. Idea jest taka:

- zapis jest wyższego poziomu,
- ale kompilator optymalizuje go do kodu porównywalnego z ręcznie napisanym stylem imperatywnym.

To ważny punkt praktyczny: nie trzeba unikać iteratorów ze strachu przed kosztami w czasie działania.

## Co zapamiętać

1. Closure to anonimowa funkcja, która może przechwytywać środowisko.
2. Rust inferuje typy domknięcia, ale raz ustalone typy stają się konkretne dla danej wartości domknięcia.
3. Sposób użycia przechwyconych danych decyduje, czy domknięcie implementuje `Fn`, `FnMut`, czy tylko `FnOnce`.
4. Iteratory są lazy: samo `iter()`, `map()` czy `filter()` nic jeszcze nie wykonuje.
5. `iter`, `iter_mut` i `into_iter` różnią się ownershipem i typem zwracanych elementów.
6. `sum` i `collect` konsumują iterator; `map` i `filter` tworzą nowe iteratory.
7. Iteratorowy styl zwykle lepiej eksponuje intencję kodu i redukuje mutowalny stan pośredni.
8. Closures i iteratory w Ruście są projektowane jako zero-cost abstractions, więc idiomatyczny kod nie musi oznaczać wolniejszego kodu.
