# 18

## Cel rozdziału

Rozdział 18 odpowiada na pytanie: w jakim sensie Rust wspiera elementy OOP i gdzie świadomie odchodzi od klasycznego modelu klas oraz dziedziczenia.

Najważniejsze tematy:

- enkapsulacja,
- polimorfizm dynamiczny przez obiekty traitowe,
- porównanie obiektów traitowych z generykami,
- implementacja klasycznego state pattern,
- bardziej „rustowe” kodowanie stanów w typach.

## Czy Rust jest obiektowy?

Książka przyjmuje praktyczne podejście: to zależy od definicji OOP.

Jeśli za „obiektowość” uznasz:

- łączenie danych i metod,
- enkapsulację,
- polimorfizm,

to Rust spełnia sporą część oczekiwań.

Jeśli za konieczny element uznasz:

- dziedziczenie klas,

to Rust nim nie jest.

## Obiekty jako dane + zachowanie

W ujęciu praktycznym Rust spełnia ten punkt przez:

- `struct` / `enum` jako nośniki danych,
- `impl` jako miejsce na metody.

Czyli np.:

```rust
struct Rectangle {
    width: u32,
    height: u32,
}

impl Rectangle {
    fn area(&self) -> u32 {
        self.width * self.height
    }
}
```

To nie jest „obiekt” w sensie klasowym, ale funkcjonalnie pokrywa podobny model.

## Enkapsulacja

Rust bardzo dobrze wspiera enkapsulację przez moduły, prywatność domyślną i `pub`.

Przykład z rozdziału:

```rust
pub struct AveragedCollection {
    list: Vec<i32>,
    average: f64,
}
```

Pola są prywatne, a API publiczne kontroluje spójność:

```rust
impl AveragedCollection {
    pub fn add(&mut self, value: i32) {
        self.list.push(value);
        self.update_average();
    }

    pub fn remove(&mut self) -> Option<i32> {
        let result = self.list.pop();
        if result.is_some() {
            self.update_average();
        }
        result
    }

    pub fn average(&self) -> f64 {
        self.average
    }

    fn update_average(&mut self) {
        let total: i32 = self.list.iter().sum();
        self.average = total as f64 / self.list.len() as f64;
    }
}
```

To jest ważny idiom Rusta: prywatne wnętrze + publiczne API, które pilnuje invariants.

## Dziedziczenie: czego nie ma

Rust nie ma klasycznego inheritance dla struktur i implementacji metod. Nie da się zdefiniować typu, który dziedziczy pola i pełne zachowanie po innym typie tak jak w klasycznych językach OOP.

Powody, dla których ludzie sięgają po inheritance, książka dzieli praktycznie na dwa:

1. **code reuse**
2. **polymorphism**

### Code reuse

W Ruście typowym substytutem są:

- kompozycja,
- domyślne implementacje traitów.

### Polimorfizm

W Ruście odpowiedzią są:

- generics + trait bounds (polimorfizm statyczny),
- trait objects (polimorfizm dynamiczny).

## Obiekty traitowe: dynamiczny polimorfizm

Obiekt traitowy to wartość wskazująca na konkretny typ implementujący dany trait, ale ukrywająca ten konkretny typ za interfejsem traitu.

Przykład bazowego traitu:

```rust
pub trait Draw {
    fn draw(&self);
}
```

Przykład przechowywania heterogenicznych komponentów GUI:

```rust
pub struct Screen {
    pub components: Vec<Box<dyn Draw>>,
}

impl Screen {
    pub fn run(&self) {
        for component in self.components.iter() {
            component.draw();
        }
    }
}
```

To umożliwia jednemu `Screen` przechowywać różne typy, byle implementowały `Draw`.

## Implementacja traitu dla wielu typów

Przykład:

```rust
pub struct Button {
    pub width: u32,
    pub height: u32,
    pub label: String,
}

impl Draw for Button {
    fn draw(&self) {
        // draw button
    }
}
```

A użytkownik biblioteki może dodać własny typ, np. `SelectBox`, i też zaimplementować `Draw`.

To jest kluczowy punkt obiektów traitowych: biblioteka może zakładać wspólne zachowanie, nie znając wszystkich konkretnych typów z góry.

## `dyn Trait` i wskaźnikowość

Obiekt traitowy występuje przez wskaźnik, np.:

- `&dyn Draw`
- `Box<dyn Draw>`

W książce główny przykład używa `Box<dyn Draw>`, bo kolekcja przechowuje własność obiektów.

## Obiekty traitowe vs generyki

Rozdział bardzo wyraźnie odróżnia dwa modele.

### Generics + trait bounds

```rust
pub struct Screen<T: Draw> {
    pub components: Vec<T>,
}
```

To daje kolekcję **jednego konkretnego typu** na instancję, np. same `Button` albo same `TextField`.

### Obiekty traitowe

```rust
pub struct Screen {
    pub components: Vec<Box<dyn Draw>>,
}
```

To daje kolekcję **wielu różnych typów** jednocześnie, np. `Button`, `TextField`, `SelectBox`.

## Static dispatch vs dynamic dispatch

### Generics

- monomorphization,
- static dispatch,
- kompilator zna typy w compile time,
- zwykle lepszy potencjał optymalizacji.

### Trait objects

- dynamic dispatch,
- decyzja, którą implementację wywołać, zapada w runtime,
- większa elastyczność,
- pewien koszt wydajnościowy i mniej optymalizacji w czasie kompilacji.

To fundamentalny trade-off: elastyczność kosztem części przewidywalności i optymalizacji.

## OOP state pattern w klasycznej wersji

Rozdział pokazuje implementację wzorca stanów dla workflow posta blogowego:

- draft,
- pending review,
- published.

Klasyczna wersja używa:

- `Post` jako głównego obiektu,
- traitu `State`,
- obiektu traitowego `Box<dyn State>` przechowywanego wewnątrz `Post`.

Schemat bazowy:

```rust
pub struct Post {
    state: Option<Box<dyn State>>,
    content: String,
}
```

API użytkownika wygląda mniej więcej tak:

```rust
let mut post = Post::new();
post.add_text("I ate a salad for lunch today");
post.request_review();
post.approve();
println!("{}", post.content());
```

## Zalety tej klasycznej wersji

- logika przejść stanów siedzi w obiektach stanu,
- `Post` nie musi mieć wielkich `match`-y po stanach,
- można rozszerzać model przez nowe stany i nowe implementacje.

## Wady klasycznej wersji w Ruście

Książka pokazuje kilka kosztów:

- sporo pośrednictwa (`Option<Box<dyn State>>`),
- część logiki jest rozsmarowana między obiekty stanu,
- niektóre błędne stany są nadal reprezentowalne i trzeba je blokować zachowaniem w czasie działania,
- występuje powiązanie między stanami przy przejściach.

To działa, ale nie wykorzystuje najmocniejszej strony Rusta: typów jako nośnika invariants.

## Kodowanie stanów w typach

Bardziej „rustowe” podejście polega na tym, żeby różne stany były różnymi typami, a przejścia między stanami były transformacjami typów.

Schemat:

```rust
pub struct Post {
    content: String,
}

pub struct DraftPost {
    content: String,
}
```

Tworzenie zaczyna się od draftu:

```rust
impl Post {
    pub fn new() -> DraftPost {
        DraftPost {
            content: String::new(),
        }
    }

    pub fn content(&self) -> &str {
        &self.content
    }
}
```

Dalej przejścia stanów są jawne:

```rust
pub struct PendingReviewPost {
    content: String,
}

impl DraftPost {
    pub fn add_text(&mut self, text: &str) {
        self.content.push_str(text);
    }

    pub fn request_review(self) -> PendingReviewPost {
        PendingReviewPost {
            content: self.content,
        }
    }
}

impl PendingReviewPost {
    pub fn approve(self) -> Post {
        Post {
            content: self.content,
        }
    }
}
```

## Zysk z kodowania stanów w typach

To najważniejszy wniosek rozdziału.

Dzięki osobnym typom:

- draft nie ma metody `content`, więc nie da się przypadkiem odczytać nieopublikowanej treści,
- pending review też nie expose’uje tego, czego nie powinien,
- niepoprawne przejścia stają się błędami kompilacji, a nie tylko błędami logiki runtime.

Czyli zamiast „pozwól na wszystko i pilnuj reguł wewnątrz”, dostajesz „nie reprezentuj niepoprawnych stanów w ogóle”.

## Trade-off dwóch wersji

### Wersja trait-object / klasyczny state pattern

- bliższa klasycznemu OOP,
- ukrywa stany bardziej całkowicie,
- łatwiejsza do rozszerzania o nowe zachowania w ramach znanego wzorca,
- ale słabiej wykorzystuje typy do egzekwowania poprawności.

### Wersja typowa dla Rusta

- mniej „obiektowa” w klasycznym sensie,
- więcej informacji zakodowanych w typach,
- więcej bezpieczeństwa w compile time,
- czasem trochę mniej podobna do wzorców znanych z OOP.

## Co zapamiętać

1. Rust wspiera dane + metody oraz enkapsulację, ale nie ma klasycznego dziedziczenia klas.
2. `pub` i prywatność modułów są podstawowym narzędziem enkapsulacji.
3. Trait objects (`dyn Trait`) służą do dynamicznego polimorfizmu i przechowywania różnych typów pod wspólnym interfejsem.
4. `Vec<Box<dyn Draw>>` pozwala na heterogeniczne kolekcje wartości implementujących ten sam trait.
5. Generyki dają static dispatch i monomorfizację, a obiekty traitowe dają dynamic dispatch i większą elastyczność w czasie działania.
6. Klasyczny state pattern da się napisać w Ruście, ale nie zawsze jest to najbardziej idiomatyczne rozwiązanie.
7. Rust często zyskuje przewagę wtedy, gdy zamiast wzorców działających głównie w czasie działania koduje poprawne stany i przejścia bezpośrednio w typach.
8. Jeśli da się uczynić niepoprawny stan niereprezentowalnym, zwykle warto to zrobić.
