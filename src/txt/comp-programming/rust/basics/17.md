# 17

## Cel rozdziału

Rozdział 17 wprowadza async w Ruście: `Future`, `async`, `await`, streamy oraz relację między future’ami, taskami i wątkami. To drugi główny model współbieżności obok wątków z rozdziału 16.

## Async: po co

Async jest przydatny wtedy, gdy operacje często **czekają**:

- na sieć,
- na I/O,
- na timer,
- na wiadomość z kanału,
- na inne zdarzenie zewnętrzne.

To model szczególnie dobry dla zadań **I/O-bound** i mocno współbieżnych.

## Future

`Future` to wartość, która może nie być gotowa teraz, ale będzie gotowa później.

Najważniejsza intuicja:

- iterator daje kolejne elementy synchronicznie,
- future daje jeden wynik asynchronicznie.

Rozdział podkreśla, że future’y są **leniwe**: samo ich utworzenie nic jeszcze nie uruchamia.

## `async fn`

Najwygodniejsza forma tworzenia future’a:

```rust
async fn page_title(url: &str) -> Option<String> {
    // ...
}
```

`async fn` nie zwraca wyniku bezpośrednio; semantycznie zwraca future, który po wykonaniu da wynik zadeklarowanego typu.

Można też tworzyć async block:

```rust
let fut = async {
    42
};
```

## `.await`

`await` czeka na gotowość future’a:

```rust
let response = trpl::get(url).await;
let text = response.text().await;
```

Kluczowe:

- `await` działa tylko w `async fn` albo `async { ... }`,
- to punkt, w którym task może się zatrzymać i oddać sterowanie środowisku wykonawczemu,
- `await` jest postfixowe (`fut.await`), nie prefixowe.

## Runtime i executor

Future sam z siebie nie „biegnie”. Potrzebne jest środowisko wykonawcze, które:

- przechowuje taski,
- je polluje,
- budzi je, gdy mogą zrobić dalszy postęp.

W książce rolę warstwy pomocniczej pełni `trpl`, a uruchamianie top-level async kodu robi:

```rust
trpl::block_on(async {
    // async code
});
```

To jest most między kodem synchronicznym a async.

## Leniwość future’ów

Rozdział mocno to akcentuje: future nic nie robi, dopóki nie zostanie:

- `await`-owany,
- uruchomiony przez środowisko wykonawcze,
- albo włączony do większej kompozycji future’ów, która ostatecznie zostanie uruchomiona.

To różni async Rust m.in. od `thread::spawn`, które uruchamia pracę od razu.

## Współbieżność async vs wątki

Async nie musi tworzyć nowego wątku OS dla każdej operacji. Wiele zadań może współdzielić ten sam wątek i przekazywać sobie wykonanie przy punktach `await`.

To daje inny kompromis niż wątki:

- mniej kosztów na task,
- dużo dobra dla I/O-bound workloads,
- ale też wymaga świadomego pilnowania punktów oddawania kontroli.

## Taski

Runtime może uruchamiać async pracę jako taski. W książce pojawia się API podobne do:

```rust
let handle = trpl::spawn_task(async {
    // ...
});
```

Task jest do async tym, czym wątek jest do kodu synchronicznego, ale jest lżejszy i zarządzany przez środowisko wykonawcze, nie bezpośrednio przez OS.

## Czekanie na task

Join handle taska sam jest future’em, więc czekanie wygląda tak:

```rust
handle.await.unwrap();
```

To odpowiednik `join()` z wątków, ale wpisany w model async.

## `join!` / łączenie future’ów

Można uruchamiać kilka future’ów równocześnie i czekać, aż wszystkie się skończą.

Przykład schematyczny:

```rust
let fut1 = async {
    // ...
};

let fut2 = async {
    // ...
};

trpl::join(fut1, fut2).await;
```

Sens:

- oba future’y robią postęp współbieżnie,
- wynik przychodzi dopiero, gdy oba są gotowe.

Rozdział podkreśla też, że konkretna implementacja `join` może być fair, czyli polling obu future’ów może odbywać się naprzemiennie i równomiernie.

## `select` / wyścig future’ów

Drugi ważny wzorzec to uruchomienie kilku future’ów i wzięcie wyniku tego, który skończy pierwszy. Książka pokazuje to przez `select`, m.in. jako bazę do budowy `timeout`.

Idea:

- dwa future’y ruszają współbieżnie,
- pierwszy gotowy wygrywa,
- drugi przestaje być dalej potrzebny.

To jest ważny wzorzec dla timeoutów, wyścigu kilku źródeł danych, fallbacków itd.

## Cancellation przez drop

Jeśli future nie zostanie doprowadzony do końca i po prostu przestanie istnieć, to zostaje anulowany przez `drop`. W async Rust anulowanie jest więc ściśle związane z zarządzaniem własnością obiektu future’a.

To ważne przy `select`, timeoutach i przerywaniu pracy po wygraniu przez inny future.

## Message passing w async

Kanały mają też wersje async. Schemat wygląda podobnie do kanałów z rozdziału 16:

```rust
let (tx, mut rx) = trpl::channel();
```

Wysyłanie:

```rust
tx.send(value);
```

Odbiór:

```rust
let msg = rx.recv().await;
```

Różnica względem wersji synchronicznej:

- `recv` jest future’em,
- nie blokuje wątku, tylko oddaje sterowanie środowisku wykonawczemu, jeśli nic jeszcze nie przyszło.

## Wiele wiadomości i iteracyjny odbiór

Async receiver naturalnie reprezentuje strumień wiadomości w czasie. To prowadzi do kolejnej abstrakcji: streamów.

## Streamy

Stream to asynchroniczny odpowiednik iteratora: daje **kolejne** wartości, ale w czasie i asynchronicznie.

Różnica względem iteratora:

- iterator jest synchroniczny,
- stream jest asynchroniczny.

Rozdział pokazuje też, że z iteratora można zrobić stream i używać go podobnie do znanego modelu iteracyjnego.

Przykład schematyczny:

```rust
use trpl::StreamExt;

let stream = trpl::stream_from_iter(vec![1, 2, 3].into_iter().map(|n| n * 2));

trpl::block_on(async {
    let mut stream = stream;
    while let Some(value) = stream.next().await {
        println!("{value}");
    }
});
```

## `StreamExt`

Tak jak przy iteratorach są wygodne metody adapters / helpers, tak przy streamach często korzysta się z traitów rozszerzających, np. `StreamExt`, żeby mieć dostęp do metod takich jak `next()`.

## Yielding i cooperative multitasking

Bardzo ważny praktyczny punkt rozdziału: async oddaje sterowanie środowisku wykonawczemu **tylko** w punktach `await`.

To oznacza, że jeśli future robi długo CPU-bound pracę bez ani jednego `await`, może zagłodzić inne future’y.

Książka pokazuje dwa sposoby oddawania kontroli:

- sztucznie przez async sleep,
- lepiej: jawnie przez coś w rodzaju `yield_now().await`.

To jest cooperative multitasking: task sam decyduje, kiedy oddaje czas innym.

## `timeout` jako własna abstrakcja async

Rozdział pokazuje budowę własnego helpera `timeout`, opartego na:

- przyszłości właściwej pracy,
- timer future,
- `select` między nimi.

To ważny wniosek architektoniczny: future’y dobrze się **komponują**, więc można z prostych elementów budować coraz bogatsze abstrakcje.

## `Future` trait: zgrubnie

Książka zagląda też pod maskę. Sedno:

- future implementuje trait `Future`,
- środowisko wykonawcze go polluje,
- wynik pollingu to w uproszczeniu „gotowe” albo „jeszcze nie”.

Czyli async/await jest wysokopoziomową składnią nad bardziej podstawowym mechanizmem pollowania.

## `Pin` / `Unpin` i traitowe detale async

Rozdział tylko lekko dotyka tych tematów, ale warto zapamiętać:

- bardziej zaawansowane kombinacje future’ów mogą wymagać pinowania,
- nie wszystkie future’y są swobodnie przesuwalne w pamięci,
- przy bardziej ręcznej pracy z future’ami pojawiają się `Pin`, `Unpin`, `Context`, `Poll`.

Na poziomie codziennego użycia `async`/`await` zwykle nie trzeba nimi zarządzać ręcznie, ale warto wiedzieć, skąd biorą się bardziej techniczne komunikaty kompilatora.

## Futures, tasks, threads — różnice

Rozdział kończy się ważnym porównaniem:

| Pojęcie | Rola |
|---|---|
| `Future` | najmniejsza jednostka async pracy; opis czegoś, co kiedyś da wynik |
| task | jednostka uruchomienia future’a / grupy future’ów zarządzana przez środowisko wykonawcze |
| thread | jednostka zarządzana przez OS, dobra też dla pracy synchronicznej i CPU-bound |

### Reguły praktyczne z książki

- gdy praca jest mocno **CPU-bound** i dobrze się równolegli → często lepsze są wątki,
- gdy praca jest mocno **I/O-bound** i bardzo współbieżna → często lepszy jest async,
- w praktyce często używa się **obu naraz**.

## Async + threads razem

To nie są konkurencyjne religie. Runtime async sam może używać wielu wątków pod spodem, a aplikacja może:

- mieć wątki do ciężkiej pracy blokującej / CPU-bound,
- używać async do orkiestracji, komunikacji i I/O.

To bardzo częsty wzorzec w realnych systemach.

## Co zapamiętać

1. `async fn` i `async { ... }` tworzą future’y, a `.await` czeka na ich wynik.
2. Future’y są leniwe: nic nie robią, dopóki środowisko wykonawcze ich nie uruchamia ani nie polluje.
3. Async potrzebuje środowiska wykonawczego; `main` samo z siebie nim nie jest.
4. Taski są lżejsze od wątków i dobrze nadają się do wysokiej współbieżności I/O-bound.
5. `join`/`join!` służy do czekania na wiele future’ów, a `select` do wyścigu i wzięcia pierwszego gotowego wyniku.
6. Porzucenie future’a zwykle oznacza jego anulowanie przez `drop`.
7. Stream to asynchroniczny odpowiednik iteratora: wiele wartości, ale dostarczanych w czasie.
8. Async działa kooperacyjnie: bez punktów `await` / `yield` jeden future może zagłodzić inne.
9. Wątki i async są narzędziami komplementarnymi, a nie wzajemnie wykluczającymi się.
