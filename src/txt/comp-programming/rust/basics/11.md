# 11

## Cel rozdziału

Rozdział 11 opisuje mechanikę automatycznych testów w Ruście: jak je pisać, uruchamiać i organizować. Rustowy test harness jest bardzo prosty semantycznie: test to zwykła funkcja, którą runner uruchamia i oznacza jako pass/fail.

## Czym jest test w Ruście

Typowy test robi trzy rzeczy:

1. przygotowuje dane,
2. uruchamia kod,
3. sprawdza wynik.

Minimalna forma:

```rust
#[test]
fn it_works() {
    let result = 2 + 2;
    assert_eq!(result, 4);
}
```

`#[test]` to atrybut mówiący test runnerowi, że dana funkcja ma zostać uruchomiona jako test.

## Jak test przechodzi lub pada

Test przechodzi, jeśli zakończy się bez panicu. Pada, jeśli:

- panicuje,
- albo asercja panicuje,
- albo zwróci `Err` w wariancie testu opartym o `Result`.

## Podstawowe asercje

### `assert!`

Używaj, gdy chcesz sprawdzić warunek logiczny:

```rust
assert!(larger.can_hold(&smaller));
assert!(!smaller.can_hold(&larger));
```

### `assert_eq!` i `assert_ne!`

Najczęstszy przypadek to porównanie wartości:

```rust
assert_eq!(add_two(2), 4);
assert_ne!(some_value, forbidden_value);
```

Przewaga nad gołym `assert!(a == b)`:

- lepszy komunikat o błędzie,
- pokazuje wartości lewego i prawego argumentu.

Wymagania techniczne:

- typy muszą implementować `PartialEq`,
- przy wypisywaniu błędu także `Debug`.

Dla własnych struktur zwykle wystarczy:

```rust
#[derive(PartialEq, Debug)]
struct MyType {
    // ...
}
```

## Własne komunikaty błędów

Do asercji można dodać własny komunikat:

```rust
assert!(
    greeting.contains(name),
    "Greeting did not contain name, value was `{greeting}`"
);
```

To jest przydatne szczególnie wtedy, gdy sam warunek nie mówi jeszcze jasno, co poszło źle.

## Testy oczekujące panicu

Jeśli poprawne zachowanie polega na panicu, używa się `#[should_panic]`:

```rust
#[test]
#[should_panic]
fn greater_than_100() {
    Guess::new(200);
}
```

Taki test przechodzi wtedy, gdy kod rzeczywiście spanikuje.

### `expected = ...`

Aby zawęzić, *dlaczego* panic miał się wydarzyć:

```rust
#[test]
#[should_panic(expected = "less than or equal to 100")]
fn greater_than_100() {
    Guess::new(200);
}
```

To chroni przed sytuacją, w której test przechodzi tylko dlatego, że kod spanikował z zupełnie innego powodu.

## Testy zwracające `Result`

Test nie musi panicować. Może zwracać `Result<(), E>`:

```rust
#[test]
fn it_works() -> Result<(), String> {
    if 2 + 2 == 4 {
        Ok(())
    } else {
        Err(String::from("two plus two does not equal four"))
    }
}
```

Zalety:

- można używać `?` wewnątrz testu,
- łatwiej pisać testy składające się z wielu operacji, które same zwracają `Result`.

Ograniczenie: nie łączy się tego z `#[should_panic]`.

## `cargo test`

Podstawowe uruchomienie:

```bash
cargo test
```

To:

- kompiluje projekt w trybie testowym,
- buduje test binary,
- uruchamia test harness.

Rust uruchamia testy równolegle i domyślnie przechwytuje stdout dla testów, które przechodzą.

## Argumenty do Cargo i do test binary

Składnia:

```bash
cargo test -- --test-threads=1
```

To ważne rozróżnienie:

- argumenty przed `--` trafiają do `cargo test`,
- argumenty po `--` trafiają do test runnera.

## Równoległość testów

Domyślnie testy lecą równolegle. To jest szybkie, ale wymaga, żeby testy nie zależały od wspólnego stanu.

Jeśli trzeba uruchamiać sekwencyjnie:

```bash
cargo test -- --test-threads=1
```

Przydaje się np. wtedy, gdy testy:

- zapisują do tych samych plików,
- używają wspólnych env varów,
- modyfikują wspólne globalne zasoby.

## Pokazywanie stdout

Domyślnie output z przechodzących testów jest ukrywany. Aby go zobaczyć:

```bash
cargo test -- --show-output
```

Jeśli test pada, jego stdout i tak pojawia się w raporcie błędu.

## Uruchamianie podzbioru testów

Pojedynczy test po nazwie:

```bash
cargo test one_hundred
```

Filtrowanie po fragmencie nazwy:

```bash
cargo test add
```

To uruchomi wszystkie testy, których nazwy zawierają `add`.

Ponieważ pełna nazwa zawiera też moduł, można filtrować również po nazwie modułu.

## Ignorowanie testów

Dla testów drogich / wolnych:

```rust
#[test]
#[ignore]
fn expensive_test() {
    // ...
}
```

Zwykłe `cargo test` ich nie uruchomi.

Uruchomienie tylko ignorowanych:

```bash
cargo test -- --ignored
```

Uruchomienie wszystkich, także ignorowanych:

```bash
cargo test -- --include-ignored
```

## Organizacja testów: unit vs integration

Rustowa praktyka rozróżnia dwa główne typy testów:

| Typ | Gdzie | Co testuje |
|---|---|---|
| unit tests | w `src/`, obok kodu | małe fragmenty kodu, także prywatne interfejsy |
| integration tests | w `tests/` | publiczne API, zachowanie z perspektywy zewnętrznego użytkownika |

## Unit tests

Konwencja:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_adds_two() {
        assert_eq!(add_two(2), 4);
    }
}
```

### Po co `#[cfg(test)]`

`#[cfg(test)]` mówi kompilatorowi, żeby ten moduł był kompilowany tylko przy `cargo test`, a nie przy zwykłym `cargo build`.

To:

- skraca zwykły build,
- nie wrzuca testowego kodu do końcowego artefaktu.

### `use super::*`

Ponieważ moduł `tests` jest zagnieżdżony, typowy idiom to import wszystkiego z modułu nadrzędnego:

```rust
use super::*;
```

Dzięki temu test ma bezpośredni dostęp do kodu, który testuje.

## Testowanie prywatnych funkcji

Rust na to pozwala. Testy wewnętrzne to zwykły child module, więc mogą używać prywatnych elementów modułu nadrzędnego.

Przykład:

```rust
fn internal_adder(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn internal() {
        assert_eq!(internal_adder(2, 2), 4);
    }
}
```

To świadoma cecha języka, nie hack.

## Integration tests

Pliki w katalogu `tests/` są kompilowane jako osobne crate’y. Dlatego test integracyjny używa Twojej biblioteki tak, jak używałby jej dowolny zewnętrzny klient.

Przykład:

```rust
use adder::add_two;

#[test]
fn it_adds_two() {
    assert_eq!(4, add_two(2));
}
```

Kluczowe konsekwencje:

- testy integracyjne widzą tylko publiczne API,
- każdy plik w `tests/` jest osobnym crate’em,
- dlatego trzeba importować bibliotekę po nazwie crate’a.

## Wspólny kod pomocniczy w integration tests

Nie wrzucaj helperów do `tests/common.rs`, jeśli nie chcesz osobnej sekcji testów z „0 tests”. Zamiast tego użyj submodułu, np.:

```text
tests/
├── common/
│   └── mod.rs
└── integration_test.rs
```

W pliku testowym:

```rust
mod common;
```

To pozwala współdzielić setup bez traktowania helpera jako osobnego pliku testowego.

## Testy dla binarki

Jeśli projekt ma tylko `src/main.rs` i nie ma `src/lib.rs`, nie da się sensownie pisać integration tests importujących logikę binarki przez `use`. Dlatego idiomatyczny układ dla większych CLI to:

- logika w `src/lib.rs`,
- cienkie `src/main.rs`, które tylko odpala bibliotekę.

Dzięki temu testy integracyjne mogą testować właściwy kod przez publiczne API biblioteki.

## Co zapamiętać

1. Test w Ruście to zwykła funkcja oznaczona `#[test]`.
2. Test przechodzi, jeśli nie panicuje; może też zwracać `Result<(), E>`.
3. `assert!`, `assert_eq!` i `assert_ne!` są podstawowymi narzędziami weryfikacji.
4. `#[should_panic]` służy do sprawdzania, że kod ma panicować, a `expected = ...` zawęża przyczynę.
5. `cargo test` uruchamia testy równolegle; `-- --test-threads=1` wyłącza równoległość.
6. `-- --show-output` pokazuje stdout także z przechodzących testów.
7. Unit tests siedzą obok kodu i mogą testować prywatne funkcje.
8. Integration tests siedzą w `tests/` i testują wyłącznie publiczne API jak zewnętrzny użytkownik.
9. Dla projektów binarnych sensowne testowanie zwykle oznacza wyniesienie logiki do `src/lib.rs`.
