# 09

## Cel rozdziału

Rozdział 9 porządkuje obsługę błędów w Ruście. Główna idea jest prosta:

- **błędy nieodwracalne** → `panic!`
- **błędy odwracalne / oczekiwane** → `Result<T, E>`

Rust nie ma wyjątków w stylu wielu innych języków. Zamiast tego wymusza jawne modelowanie możliwości błędu.

## Dwa poziomy błędów

| Typ problemu | Narzędzie | Znaczenie |
|---|---|---|
| nieodwracalny | `panic!` | program jest w stanie, z którego nie powinien kontynuować |
| odwracalny | `Result<T, E>` | wywołujący może zdecydować, co zrobić dalej |

To ważne semantycznie: wybierając `panic!`, odbierasz wywołującemu możliwość reakcji. Zwracając `Result`, przekazujesz decyzję wyżej.

## `panic!`

Najprostszy panic:

```rust
panic!("crash and burn");
```

W praktyce panic pojawia się na dwa sposoby:

- wywołujesz `panic!` jawnie,
- wykonujesz operację, która narusza kontrakt, np. wyjście poza zakres indeksowania.

### Unwinding vs abort

Domyślnie panic robi **unwinding** stosu:

- stack jest odwijany,
- po drodze zwalniane są zasoby,
- program kończy działanie.

Alternatywa to **abort**: natychmiastowe zakończenie procesu bez odwijania.

Konfiguracja dla release:

```toml
[profile.release]
panic = 'abort'
```

To może zmniejszyć rozmiar binarki kosztem utraty cleanupu podczas panicu.

## Typowe paniki

Klasyczny przykład:

```rust
let v = vec![1, 2, 3];

v[99];
```

Rust woli przerwać program niż dopuścić do niebezpiecznego odczytu pamięci poza strukturą danych.

## Backtrace

Przy panicu można poprosić o backtrace:

```bash
RUST_BACKTRACE=1 cargo run
```

Jak czytać:

- zacznij od góry,
- szukaj pierwszej ramki wskazującej na plik, który napisałeś,
- to zwykle najlepszy punkt startowy do diagnozy.

Pełniejsza wersja:

```bash
RUST_BACKTRACE=full cargo run
```

## `Result<T, E>`

Podstawowy typ dla błędów odwracalnych:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

- `Ok(T)` zawiera wartość sukcesu,
- `Err(E)` zawiera informację o błędzie.

To standardowy kontrakt API dla operacji, które mogą się nie udać.

## Obsługa `Result` przez `match`

Podstawowy wzorzec:

```rust
use std::fs::File;

let greeting_file_result = File::open("hello.txt");

let greeting_file = match greeting_file_result {
    Ok(file) => file,
    Err(error) => panic!("Problem opening the file: {error:?}"),
};
```

To jawna forma rozróżnienia sukcesu i błędu.

## Rozróżnianie rodzajów błędów

Na `Err` można wykonać dalszy `match`, np. po `error.kind()`:

```rust
use std::fs::File;
use std::io::ErrorKind;

let greeting_file = match File::open("hello.txt") {
    Ok(file) => file,
    Err(error) => match error.kind() {
        ErrorKind::NotFound => match File::create("hello.txt") {
            Ok(fc) => fc,
            Err(error) => panic!("Problem creating the file: {error:?}"),
        },
        other_error => panic!("Problem opening the file: {other_error:?}"),
    },
};
```

To wzorzec „obsłuż konkretny przypadek, a resztę potraktuj jako błąd krytyczny”.

## `unwrap` i `expect`

### `unwrap`

```rust
let greeting_file = File::open("hello.txt").unwrap();
```

- przy `Ok` zwraca wartość,
- przy `Err` panikuje.

### `expect`

```rust
let greeting_file = File::open("hello.txt")
    .expect("hello.txt should be included in this project");
```

`expect` robi to samo co `unwrap`, ale pozwala dodać lepszy komunikat.

Praktycznie:

- w kodzie docelowym `expect` zwykle jest lepsze niż `unwrap`,
- komunikat powinien opisywać założenie, które miało być prawdziwe.

## Propagowanie błędów

Zamiast obsługiwać błąd lokalnie, można zwrócić go wywołującemu.

Wersja ręczna:

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let username_file_result = File::open("hello.txt");

    let mut username_file = match username_file_result {
        Ok(file) => file,
        Err(e) => return Err(e),
    };

    let mut username = String::new();

    match username_file.read_to_string(&mut username) {
        Ok(_) => Ok(username),
        Err(e) => Err(e),
    }
}
```

To jest poprawne, ale rozwlekłe.

## Operator `?`

Najważniejszy skrót rozdziału:

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username_file = File::open("hello.txt")?;
    let mut username = String::new();
    username_file.read_to_string(&mut username)?;
    Ok(username)
}
```

Semantyka `?`:

- jeśli `Ok`, wyciąga wartość i kontynuuje,
- jeśli `Err`, natychmiast zwraca błąd z całej funkcji.

To praktycznie syntactic sugar dla `match` z early return.

## `?` i konwersja błędów

`?` nie tylko zwraca błąd, ale może też konwertować go przez `From`. Dzięki temu funkcja może zwracać szerszy typ błędu, a poszczególne wywołania nadal mogą zwracać różne błędy źródłowe.

## Skracanie kodu przez chaining

Ta sama funkcja może być krótsza:

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username = String::new();
    File::open("hello.txt")?.read_to_string(&mut username)?;
    Ok(username)
}
```

A jeszcze krócej przez helper ze standard library:

```rust
use std::fs;
use std::io;

fn read_username_from_file() -> Result<String, io::Error> {
    fs::read_to_string("hello.txt")
}
```

Wniosek praktyczny: najpierw trzeba rozumieć ręczny model, potem można go bezpiecznie skracać.

## Gdzie wolno używać `?`

`?` działa tylko w funkcjach, których typ zwracany jest kompatybilny z operacją:

- `Result` w funkcji zwracającej `Result`,
- `Option` w funkcji zwracającej `Option`,
- ewentualnie inne typy zgodne z mechanizmem `FromResidual`.

Nie można swobodnie mieszać `Option` i `Result` bez jawnej konwersji.

## `?` na `Option`

Przykład:

```rust
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}
```

Tu `?`:

- zwróci `None`, jeśli nie ma pierwszej linii,
- inaczej przepuści dalej zawartość `Some(...)`.

## `main` może zwracać `Result`

Jeśli chcesz używać `?` w `main`, możesz zmienić jego sygnaturę:

```rust
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let _greeting_file = File::open("hello.txt")?;
    Ok(())
}
```

Wtedy:

- `Ok(())` oznacza sukces procesu,
- `Err(...)` kończy program z niezerowym exit code.

## Kiedy `panic!`, a kiedy `Result`

Domyślna zasada z rozdziału:

- dla funkcji, które **mogą normalnie failować**, zwracaj `Result`,
- `panic!` zostaw na sytuacje, gdzie dalsze działanie nie ma sensu albo oznacza błąd programisty.

## Dobre sytuacje dla `panic!`

### 1. Przykłady, prototypy, testy

Tam `unwrap` / `expect` bywają akceptowalne, bo:

- chcesz zwięzłości,
- nie ustaliłeś jeszcze finalnej strategii obsługi błędów,
- w testach panic i tak oznacza porażkę testu.

### 2. Masz wiedzę, której kompilator nie ma

Jeśli wiesz, że operacja logicznie nie może się nie udać, można użyć `expect` i udokumentować założenie:

```rust
use std::net::IpAddr;

let home: IpAddr = "127.0.0.1"
    .parse()
    .expect("Hardcoded IP address should be valid");
```

### 3. Zły stan programu / złamany kontrakt

Panic jest sensowny, gdy naruszony został invariant lub contract, np.:

- dane są sprzeczne,
- wartość jest nieprawidłowa i dalsze działanie byłoby niebezpieczne,
- wywołujący podał argumenty, które łamią wymagania API.

## Lepsze modelowanie przez typy

Rozdział kończy się ważną ideą: zamiast rozrzucać walidację wszędzie, można zakodować poprawność w typie.

Przykład `Guess`, który dopuszcza tylko wartości 1..=100:

```rust
pub struct Guess {
    value: i32,
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            panic!("Guess value must be between 1 and 100, got {value}.");
        }

        Guess { value }
    }

    pub fn value(&self) -> i32 {
        self.value
    }
}
```

To przenosi walidację do miejsca konstrukcji typu i upraszcza resztę programu.

## Co zapamiętać

1. `panic!` służy do błędów nieodwracalnych i zwykle oznacza błąd programisty albo zły stan programu.
2. `Result<T, E>` służy do błędów odwracalnych i daje wywołującemu decyzję, co zrobić dalej.
3. `unwrap` i `expect` panikują przy błędzie; `expect` jest lepsze, bo dokumentuje założenie.
4. Operator `?` to podstawowy idiom propagacji błędów bez boilerplate’u.
5. `?` działa tylko w funkcjach o kompatybilnym typie zwracanym.
6. `main` może zwracać `Result<(), Box<dyn Error>>`, co pozwala używać `?` także tam.
7. Jeśli błąd jest oczekiwanym elementem normalnego działania, zwracaj `Result`, nie `panic!`.
8. Jeśli poprawność da się wyrazić typem, lepiej to zrobić niż wielokrotnie sprawdzać warunki w runtime.
