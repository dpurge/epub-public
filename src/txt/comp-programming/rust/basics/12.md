# 12

## Cel rozdziału

Rozdział 12 buduje mały klon `grep` (`minigrep`) i przy okazji pokazuje praktyczny układ binarki CLI w Ruście. To rozdział o składaniu wcześniej poznanych elementów w sensowną całość: argumenty, pliki, błędy, testy, zmienne środowiskowe i `stderr`.

## Cel programu

`minigrep` przyjmuje:

- tekst do wyszukania,
- ścieżkę do pliku,

czyta plik i wypisuje linie zawierające zapytanie.

## Argumenty linii poleceń

Podstawowy odczyt argumentów:

```rust
use std::env;

let args: Vec<String> = env::args().collect();
```

Ważne szczegóły:

- `env::args()` zwraca iterator,
- `collect()` zbiera argumenty do `Vec<String>`,
- `args[0]` to nazwa uruchomionego programu,
- realne argumenty użytkownika zaczynają się od indeksu `1`.

Typowy przebieg wywołania:

```bash
cargo run -- searchstring example-filename.txt
```

`--` rozdziela argumenty Cargo od argumentów programu.

### Uwaga o Unicode

`std::env::args()` panikuje przy argumentach zawierających niepoprawne Unicode. Jeśli aplikacja musi obsługiwać takie przypadki, używa się `args_os()` i `OsString`.

## Odczyt pliku

Najprostsza wersja:

```rust
use std::fs;

let contents = fs::read_to_string(file_path)
    .expect("Should have been able to read the file");
```

`fs::read_to_string`:

- otwiera plik,
- czyta całość do `String`,
- zwraca `Result<String, io::Error>`.

## Problem początkowej wersji

Wczesna wersja `main` robi za dużo naraz:

- parsuje argumenty,
- buduje konfigurację,
- czyta plik,
- wykonuje logikę,
- obsługuje błędy.

Rozdział prowadzi do klasycznego refaktoru CLI:

- `main` ma być cienki,
- logika ma trafić do biblioteki,
- błędy mają być raportowane czytelnie.

## `Config`

Powiązane parametry warto zgrupować w strukturę:

```rust
struct Config {
    query: String,
    file_path: String,
    ignore_case: bool,
}
```

To poprawia czytelność, bo od razu widać, że te wartości opisują konfigurację działania programu.

## `Config::build`

Początkowe `new` zostaje zamienione na `build`, bo konstruktor może failować.

Schemat:

```rust
impl Config {
    fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();
        let ignore_case = std::env::var("IGNORE_CASE").is_ok();

        Ok(Config {
            query,
            file_path,
            ignore_case,
        })
    }
}
```

### Dlaczego `clone`

W rozdziale `Config` przechowuje własne `String`, a nie referencje do `args`, bo to upraszcza model ownership. To trochę kosztuje, ale tylko raz na starcie programu i dla małych danych konfiguracyjnych.

## Cienki `main`

Docelowy podział odpowiedzialności:

- `main` zbiera argumenty,
- buduje `Config`,
- uruchamia `run`,
- obsługuje błędy,
- kończy proces odpowiednim exit code.

Schemat końcowy:

```rust
use std::env;
use std::process;

fn main() {
    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        eprintln!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    if let Err(e) = run(config) {
        eprintln!("Application error: {e}");
        process::exit(1);
    }
}
```

To jest bardzo ważny idiom w projektach binarnych Rusta.

## `run(config)`

Reszta programu ląduje w osobnej funkcji:

```rust
use std::error::Error;
use std::fs;

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    for line in search(&config.query, &contents) {
        println!("{line}");
    }

    Ok(())
}
```

Najważniejsze:

- `run` zwraca `Result<(), Box<dyn Error>>`,
- czyta plik przez `?`,
- drukuje znalezione linie,
- zwraca `Ok(())` przy sukcesie.

`Box<dyn Error>` oznacza tutaj: „dowolny błąd implementujący trait `Error`”.

## Rozdzielenie binarki i biblioteki

Rozdział promuje układ:

- `src/main.rs` — tylko uruchomienie programu,
- `src/lib.rs` — logika, którą można testować.

To pozwala łatwo pisać testy bez odpalania binarki z CLI.

## Funkcja `search`

Interfejs funkcji wyszukiwania:

```rust
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    let mut results = Vec::new();

    for line in contents.lines() {
        if line.contains(query) {
            results.push(line);
        }
    }

    results
}
```

### Dlaczego lifetime jest jawny

Funkcja zwraca slice’y wyjęte z `contents`, więc lifetime zwracanego `Vec<&str>` musi być powiązany z lifetime’em `contents`, a nie `query`.

## TDD dla `search`

Rozdział buduje wyszukiwanie test-driven:

1. napisz failing test,
2. dopisz minimum kodu,
3. przepuść test,
4. refaktor,
5. powtarzaj.

Test dla wyszukiwania:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn one_result() {
        let query = "duct";
        let contents = "\
Rust:
safe, fast, productive.
Pick three.
Duct tape.";

        assert_eq!(vec!["safe, fast, productive."], search(query, contents));
    }
}
```

To sprawdza, że zwykłe wyszukiwanie jest case-sensitive.

## Case-insensitive search

Druga funkcja:

```rust
pub fn search_case_insensitive<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    let query = query.to_lowercase();
    let mut results = Vec::new();

    for line in contents.lines() {
        if line.to_lowercase().contains(&query) {
            results.push(line);
        }
    }

    results
}
```

Kluczowa idea:

- obniż query do lowercase,
- każdą linię też obniż do lowercase,
- porównuj już na znormalizowanych danych.

Rozdział zaznacza, że to nie jest pełna, idealna obsługa Unicode, ale dla celu dydaktycznego wystarcza.

## `IGNORE_CASE`

Tryb wyszukiwania zależy od zmiennej środowiskowej:

```rust
let ignore_case = env::var("IGNORE_CASE").is_ok();
```

Znaczenie:

- jeśli `IGNORE_CASE` jest ustawione na cokolwiek, tryb jest case-insensitive,
- jeśli nie jest ustawione, wyszukiwanie pozostaje case-sensitive.

## Wybór funkcji wyszukiwania

W `run` wybór wygląda tak:

```rust
let results = if config.ignore_case {
    search_case_insensitive(&config.query, &contents)
} else {
    search(&config.query, &contents)
};
```

To prosty wzorzec na rozdzielenie polityki konfiguracji od właściwej logiki przetwarzania.

## `stdout` vs `stderr`

Ważny detal dla CLI:

- wynik programu powinien iść na `stdout`,
- błędy powinny iść na `stderr`.

Domyślny `println!` pisze na `stdout`, więc do błędów trzeba użyć:

```rust
eprintln!("Problem parsing arguments: {err}");
```

Dzięki temu można przekierować zwykły output do pliku, a błędy nadal widzieć na ekranie.

## Czemu `stderr` ma znaczenie

Przy przekierowaniu:

```bash
cargo run -- to poem.txt > output.txt
```

- `stdout` trafia do `output.txt`,
- `stderr` nadal pojawia się na terminalu.

To jest standardowe, oczekiwane zachowanie programów CLI.

## Najważniejsze decyzje projektowe z rozdziału

| Problem | Rozwiązanie |
|---|---|
| zbyt gruby `main` | wynieś logikę do `run` i do `lib.rs` |
| luźne zmienne konfiguracyjne | zgrupuj je w `Config` |
| słabe komunikaty błędów | zwracaj `Result` i obsłuż je w `main` |
| trudne testowanie CLI | przenieś logikę wyszukiwania do biblioteki |
| konfigurowalna czułość na wielkość liter | `IGNORE_CASE` |
| mieszanie wyników i błędów | `println!` dla sukcesu, `eprintln!` dla błędów |

## Co zapamiętać

1. Dobre Rustowe CLI zwykle ma cienkie `main` i grubszą bibliotekę w `lib.rs`.
2. `env::args().collect()` to podstawowy sposób pobierania argumentów linii poleceń.
3. `fs::read_to_string` daje szybki, prosty odczyt całego pliku do `String`.
4. `Config::build` powinno zwracać `Result`, jeśli parsowanie argumentów może się nie udać.
5. `run(config) -> Result<(), Box<dyn Error>>` to idiomatyczny sposób zamknięcia logiki programu.
6. Funkcje `search` i `search_case_insensitive` są łatwe do testowania po wyniesieniu ich do biblioteki.
7. Zmienna środowiskowa `IGNORE_CASE` to prosty przykład konfiguracji niezależnej od argumentów CLI.
8. Błędy CLI powinny trafiać na `stderr`, nie na `stdout`, dlatego używa się `eprintln!`.
