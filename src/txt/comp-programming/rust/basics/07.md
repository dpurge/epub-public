# 07

## Cel rozdziału

Rozdział 7 porządkuje organizację kodu w Ruście: package, crate, moduły, ścieżki, prywatność i importy. To rozdział o strukturze projektu i API, nie o algorytmach.

## Podstawowe pojęcia

### Package

Package to jednostka zarządzana przez Cargo. Zawiera `Cargo.toml` i jeden lub więcej crate’ów.

### Crate

Crate to najmniejsza jednostka kompilacji dla `rustc`. Może być:

- **binary crate** — ma `main` i buduje wykonywalny program,
- **library crate** — nie ma `main`, eksportuje funkcjonalność do użycia gdzie indziej.

### Crate root

Crate root to plik, od którego kompilator zaczyna budowę drzewa modułów:

- `src/main.rs` dla binarki,
- `src/lib.rs` dla biblioteki.

### Package vs crate

Najważniejsza relacja:

- package zawiera crate’y,
- package może mieć wiele binary crate’ów,
- package może mieć maksymalnie jeden library crate,
- package musi mieć co najmniej jeden crate.

## Typowy układ plików

`cargo new my-project` tworzy package z jednym binary crate:

```text
my-project/
├── Cargo.toml
└── src/
    └── main.rs
```

Jeśli istnieje też `src/lib.rs`, package zawiera zarówno binarkę, jak i bibliotekę.

Dodatkowe binarki można umieszczać w `src/bin/`.

## Moduły

Moduły służą do:

- grupowania powiązanego kodu,
- budowania drzewa nazw,
- kontroli prywatności.

Przykład:

```rust
mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
        fn seat_at_table() {}
    }

    mod serving {
        fn take_order() {}
        fn serve_order() {}
        fn take_payment() {}
    }
}
```

Całość tworzy drzewo modułów zakorzenione w ukrytym module `crate`.

## Drzewo modułów

Warto myśleć o nim jak o drzewie katalogów:

```text
crate
└── front_of_house
    ├── hosting
    └── serving
```

Pojęcia praktyczne:

- moduł zewnętrzny to parent,
- moduł zagnieżdżony to child,
- moduły na tym samym poziomie to siblings.

## Deklarowanie modułów

W crate root można zadeklarować moduł:

```rust
mod garden;
```

Kompilator będzie szukał kodu modułu:

- inline w `{ ... }`, albo
- w `src/garden.rs`, albo
- w `src/garden/mod.rs`.

Dla submodułów analogicznie, ale wewnątrz katalogu modułu rodzica.

## Ścieżki

Do odwoływania się do elementów w drzewie modułów służą ścieżki.

Są dwa główne rodzaje:

| Rodzaj | Start |
|---|---|
| absolutna | od crate root (`crate`) albo od nazwy zewnętrznego crate’a |
| względna | od bieżącego modułu (`self`, `super`, lokalny identyfikator) |

Przykłady:

```rust
crate::front_of_house::hosting::add_to_waitlist();
front_of_house::hosting::add_to_waitlist();
```

## `crate`, `self`, `super`

- `crate::...` — start od root bieżącego crate’a,
- `self::...` — start od bieżącego modułu,
- `super::...` — start od modułu nadrzędnego.

Przykład z `super`:

```rust
fn fix_incorrect_order() {
    cook_order();
    super::deliver_order();
}
```

`super` jest przydatne tam, gdzie relacja „dziecko → rodzic” jest stabilna i logiczna.

## Prywatność domyślna

W Ruście wszystko jest domyślnie prywatne względem modułów nadrzędnych:

- moduły,
- funkcje,
- struktury,
- pola,
- metody,
- enumy,
- stałe.

Kod w parent module **nie** ma automatycznego dostępu do prywatnych elementów child module. Za to child widzi elementy przodków zgodnie z regułami widoczności.

## `pub`

`pub` wystawia element na zewnątrz jego bieżącego modułu.

Aby ścieżka była używalna z zewnątrz, publiczne muszą być wszystkie potrzebne etapy:

```rust
pub mod hosting {
    pub fn add_to_waitlist() {}
}
```

Samo `pub mod hosting` nie wystarczy, jeśli `add_to_waitlist` pozostaje prywatne.

## `pub` dla struct i enum

### Struct

Publiczna struktura nie oznacza automatycznie publicznych pól:

```rust
pub struct Breakfast {
    pub toast: String,
    seasonal_fruit: String,
}
```

To daje kontrolę per pole.

### Enum

Jeśli `enum` jest publiczny, jego warianty też są publiczne:

```rust
pub enum Appetizer {
    Soup,
    Salad,
}
```

To różni się od `struct`, gdzie pola pozostają prywatne bez jawnego `pub`.

## `use`

`use` tworzy skrót nazwy w danym scope. Nie ładuje modułu drugi raz i nie zmienia struktury projektu — tylko skraca zapis.

Przykład:

```rust
use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    hosting::add_to_waitlist();
}
```

Ważna zasada: `use` działa tylko w tym scope, w którym zostało zapisane.

## Idiomy `use`

### Funkcje

Dla funkcji idiomatycznie importuje się moduł rodzica, nie samą funkcję:

```rust
use crate::front_of_house::hosting;

hosting::add_to_waitlist();
```

To ułatwia rozpoznanie, że funkcja nie jest lokalna.

### Typy

Dla struktur, enumów i innych typów idiomatycznie importuje się pełną ścieżkę do typu:

```rust
use std::collections::HashMap;
```

## `as`

`as` pozwala nadać lokalny alias przy imporcie:

```rust
use std::fmt::Result;
use std::io::Result as IoResult;
```

To przydaje się głównie przy konfliktach nazw.

## `pub use`

`pub use` robi re-export: importuje nazwę do bieżącego modułu i jednocześnie udostępnia ją dalej jako część publicznego API.

```rust
pub use crate::front_of_house::hosting;
```

Dzięki temu zewnętrzny użytkownik może korzystać z krótszej ścieżki, np. `restaurant::hosting::add_to_waitlist()`, bez znajomości pełnej wewnętrznej struktury.

To ważne narzędzie projektowania API: można mieć jedną organizację wewnętrzną i inną, wygodniejszą powierzchnię publiczną.

## Import z zewnętrznych crate’ów

Po dodaniu zależności do `Cargo.toml` używasz jej przez ścieżkę zaczynającą się od nazwy crate’a:

```rust
use rand::prelude::*;
```

Standard library działa analogicznie, z tym że nie wymaga wpisu w `Cargo.toml`:

```rust
use std::collections::HashMap;
```

## Zagnieżdżone ścieżki w `use`

Jeśli kilka importów ma wspólny prefiks, można je zgrupować:

```rust
use std::{cmp::Ordering, io};
```

Albo przy wspólnej ścieżce i jednym jej nadzbiorze użyć `self`:

```rust
use std::io::{self, Write};
```

To importuje jednocześnie `std::io` i `std::io::Write`.

## Glob import

Można zaimportować wszystkie publiczne elementy modułu:

```rust
use std::collections::*;
```

To bywa wygodne, ale zwykle pogarsza czytelność i może prowadzić do konfliktów nazw. Rozdział sugeruje ostrożność; typowe zastosowania to m.in. testy i prelude-style APIs.

## Rozdzielanie modułów do osobnych plików

Duże moduły zwykle wynosi się z inline do osobnych plików.

Przykład:

`src/lib.rs`

```rust
mod front_of_house;
```

`src/front_of_house.rs`

```rust
pub mod hosting;
```

`src/front_of_house/hosting.rs`

```rust
pub fn add_to_waitlist() {}
```

Najważniejsze:

- `mod` deklaruje moduł tylko raz w drzewie,
- pozostały kod odwołuje się już ścieżkami,
- `mod` nie jest odpowiednikiem wielokrotnego `include`.

## Style ścieżek plików modułów

Wspierane są dwa style:

- nowocześniejszy / częstszy: `src/front_of_house.rs`, `src/front_of_house/hosting.rs`
- starszy: `src/front_of_house/mod.rs`, `src/front_of_house/hosting/mod.rs`

Oba działają, ale mieszanie stylów dla tego samego modułu jest błędem, a starszy `mod.rs` bywa mniej wygodny w większych projektach.

## Praktyka dla package z binarką i biblioteką

Jeśli package ma jednocześnie `src/main.rs` i `src/lib.rs`, dobra praktyka jest taka:

- logikę i drzewo modułów trzymać w `src/lib.rs`,
- `src/main.rs` zostawić jako cienki punkt wejścia wywołujący publiczne API biblioteki.

To wymusza sensowniejsze API i ułatwia reuse kodu.

## Co zapamiętać

1. Package to kontener Cargo, crate to jednostka kompilacji, a moduły organizują kod wewnątrz crate’a.
2. `src/main.rs` i `src/lib.rs` są crate rootami odpowiednio dla binarki i biblioteki.
3. Ścieżki mogą być absolutne (`crate::...`) albo względne (`self`, `super`, lokalny moduł).
4. Wszystko jest domyślnie prywatne; `pub` trzeba dodawać jawnie.
5. Publiczny moduł nie czyni automatycznie publicznymi jego elementów.
6. Publiczny `struct` nie oznacza publicznych pól, ale publiczny `enum` eksportuje warianty.
7. `use` skraca nazwy w danym scope; `pub use` dodatkowo buduje publiczne API.
8. Dla funkcji idiomatycznie importuje się moduł rodzica, dla typów — pełną ścieżkę do typu.
9. Moduły można bezpiecznie przenosić do osobnych plików bez zmiany samego drzewa modułów.
